# 1단계: 전역 Area 실행 카운터 영향

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 변경

`Area::update()`의 전역 atomic `areaRunCount` 증가는 예제 출력에만 사용되며 실행 제어에는 사용되지 않는다. `AREAUPDATE_RUN_COUNTER`로 진단 계측을 선택할 수 있게 하고 기본값은 0으로 두었다. 비활성화 시 예제 출력은 0회가 아니라 `runCount: disabled`로 표시한다. Actor FPS 계산과 Task 통계는 유지했다.

MSBuild에서 `/p:AreaRunCounterEnabled=1`을 주면 기존 카운터를 사용할 수 있다. 반경, batch 64, partition 공평성, Actor 소유권, 타이머와 Worker 정책은 변경하지 않았다. 파티션 캐싱과 예약 할당 변경은 아직 적용하지 않았다.

## 측정 조건

- `Source/AreaUpdate.sln`을 MSBuild Release x64로 빌드했다. 변경 전 카운터 사용 실행 파일과 변경 후 미사용 실행 파일을 별도 보관했다.
- 각 실행 30초, Actor 연산 추가 부하 0, signal 대기, adaptive 1ms/10ms/max16.
- 입장은 1,000ms 동안 1ms 간격 분산, uniform 배치. 14만 Actor는 맵 453×453 / 초당 이동 요청 4,000, 28만 Actor는 맵 640×640 / 8,000.
- seed 42는 사용→미사용, seed 43은 미사용→사용 순서로 실행했다. 총 8회이며 다른 빌드나 테스트를 측정 중 동시에 실행하지 않았다.
- 표는 조건별 2회 단순 평균이다. 정상 상태 FPS와 CPU를 사용했으며 CPU는 전체 논리 프로세서 대비 비율이다. CPU 집계 시작은 입장 완료 후 1초다. 서로 다른 집계 구간의 엄밀한 효율 비율로 확대 해석하지 않는다.
- WPR 없이 측정했다. 원본 결과와 실행 파일 해시는 `artifacts/area-counter-ab`에 보관했다. 기존 카운터 사용 실행 파일에는 새 diagnostics 필드가 없으며, 변경 전 소스 빌드라는 사실과 바이너리 해시로 구분했다.

## 결과

| Actor | 카운터 사용 FPS | 미사용 FPS | 사용 CPU | 미사용 CPU |
|---|---:|---:|---:|---:|
| 140,000 | 19.991 | 19.967 | 48.88% | 48.81% |
| 280,000 | 14.860 | 14.744 | 74.84% | 73.42% |

카운터 제거 후 FPS 변화는 각각 약 -0.12%, -0.78%다. 표본이 조건별 2개이므로 통계적으로 유의한 악화도 단정하지 않는다. 다만 **성능 개선은 관측되지 않았다.**

개별 실행 p99 gap bucket은 14만 사용 60/60ms, 미사용 60/70ms, 28만 사용 90/90ms, 미사용 100/90ms였다. 이 값은 버킷 경계이며 정확한 p99 지연 시간이 아니다. 28만 사용 실행 중 최대 gap 1,190ms가 한 번 있었으나 단일 최대값만으로 카운터 효과를 결론내리지 않았다.

8회 모두 측정 스크립트의 overlap=0, never_updated=0, Task live=0, pending=0 검증을 통과했다.

추가로 Release(카운터 미사용)와 Debug(카운터 사용) 솔루션 빌드 및 AreaTests가 통과했다. Release 이동·이벤트 검증은 5,000 Actor / 5초에서 전송·적용 59,656건 일치, overlap=0, 소유권 등록·탈퇴 주기 통과, Task live=0이었다. 전체 서식 검사와 명명·초기화·중괄호 검사도 통과했다.

## 판단

프로파일의 `Area::update()` 자체 21.30%를 전역 카운터 경합으로 설명할 수 없다. 전역 카운터가 이번 조건에서 낮은 CPU 활용률의 주원인이라는 가설은 지지되지 않았다. 카운터를 기본 실행 경로에서 뺀 것은 진단 계측 분리이며 측정된 성능 향상으로 보고하지 않는다.

다음에는 카운터를 끈 상태를 공통 기준으로 고정한 뒤, 파티션 인덱스 반복 계산 제거만 따로 적용·비교해야 한다. 예약 할당 감소는 그 이후 독립 변경으로 검증한다.

이후 두 단계도 진행했으며 [후속 비교 보고서](AREA-FOLLOWUP-COMPARISON.md)에 결과와 한계를 기록했다.

## 재현

`tools/experiments/Run-AreaCounterComparison.ps1`은 `bin/counter-on.exe`, `bin/counter-off.exe` 두 실행 파일을 읽는다. 이미 완료한 summary.json은 보존해 집계만 재개한다. 새 실험은 새 출력 폴더와 해당 빌드의 실행 파일을 사용해야 한다.
