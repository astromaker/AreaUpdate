# 실제 Dispatcher Worker 부하 분산 확인

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 범위

이 계측은 Actor 실행 스레드인 TaskDispatcher Worker를 대상으로 한다.
이전 Object 표본의 소속 timer Worker와 구분한다.
기존 전역 round-robin, Actor별 직렬 실행, batch/재전달 정책은 변경하지 않았다.
idle Worker 관리·stealing·풀도 추가하지 않았다.

## 기록하는 지표

- dispatch_tasks: Dispatcher 큐에서 실행·삭제한 전달 Task 수. 처리한 Actor 수와 같다고 단정하지 않는다.
- executer_tasks: 해당 스레드가 실제 TaskExecuter에서 실행한 내부 Task 수.
  인라인/지연 실행한 다른 실행기의 Task도 포함한다. 종료 확인으로 일찍 반환한 Task도 포함한다.
- batches/max_batch_tasks: 큐에서 분리해 처리한 목록의 횟수와 최대 크기.
- busy_ms: 해당 목록의 실행·삭제·완료 카운터 처리 구간의 누적 벽시계 시간.
- idle_ms: WakeSignal 대기의 누적 벽시계 시간.
- elapsed_ms: Dispatcher 스레드의 전체 생존 시간. 초기 맵 준비·입장·종료 구간도 포함한다.
- queue_mean/p50/p95/p99/max: Dispatcher 제출 직전부터 실행 시작까지의 표본 대기, 1ms 해상도.
- run_mean/max: 표본 전달 Task의 run 및 delete 구간, 고해상도 벽시계 시간.

busy_ms와 idle_ms의 합에 큐 pop/reverse 등 루프의 모든 구간이 포함되는 것은 아니다.
어느 지표도 스레드 CPU 시간과 같지 않으며, 잠금 대기·OS 실행 중단이 섞일 수 있다.
하나의 전달 Task가 내부 Task 여러 개를 처리할 수 있으므로 건수와 실행 시간을 함께 본다.
Worker별 p99의 최댓값은 전체 Task 분포의 p99가 아니다.
0ms bucket은 1ms 미만 대기를 포함한다. 200ms 이상은 histogram 마지막 bucket에 합친다.

## 구현과 안전성

기본 DispatcherProfileStride=0은 계측 OFF다.
256이면 각 Worker의 개별 배정 순번 기준으로 256회 중 한 번을 선택한다.
전체 제출 순번을 단순히 256으로 나누어 특정 Worker만 고르는 문제를 피했다.
이는 주기적 표본이므로 반복 부하 패턴과 겹칠 가능성을 완전히 배제하지는 않는다.

통계는 Worker 자신만 쓰는 별도 블록에 기록하고 통계용 전역 atomic이나 로그 mutex는 추가하지 않았다.
이 블록은 계측 ON일 때 스레드 시작 전에 한 번 할당하며 큐/알림 상태와 객체 저장 공간을 분리했다.
작업마다 통계 블록을 생성하거나 재사용하는 풀이 아니다.
건수·batch 시간은 전체 기록, 큐 대기·개별 run 시간은 표본 기록이다.
Task의 기존 밀리초 제출 시각 필드를 사용해 Task 크기를 늘리지 않았다.
순번/완료 카운터의 기존 동기화는 유지한다.

안전한 종료 후 조회를 위해 기존 소멸자의 종료 절차를 shutdown으로 분리했다.
생산자를 먼저 중단한 뒤 wait_idle → Worker 중단·join → 통계 복사를 수행한다.
shutdown끼리 또는 shutdown과 post/run_task를 동시에 호출하는 사용법은 지원하지 않는다.
종료 후 새 제출은 거부하고 전달받은 Task 소유권은 정리한다.
worker_statistics는 join이 끝난 상태에서만 허용한다.
RuntimeBackend도 Core Worker join 이후 Dispatcher shutdown·통계 보관·오브젝트 정리 순서를 사용한다.

계측 OFF에서는 통계 블록을 할당하지 않지만 지원용 포인터와 비활성 검사 자체는 남는다.
정확한 Task 소멸과 스레드 종료 이후에만 읽으므로 실행 중 비원자 통계의 동시 조회는 없다.
생산자 중단은 기존 소멸자와 마찬가지로 호출자의 수명 관리 계약이다.

## 검증용 강제 불균형

기존 round-robin 테스트를 계측했다. Worker 0의 첫 Task를 80ms 유지하고,
나머지 Worker 3개의 작업이 먼저 끝난 상태에서 Worker 0에 다음 작업을 배정했다.
Release 회귀 로그에서는 다음을 기록했다.

| Worker | 전달 Task | batch 실행 벽시계 | 최대 큐 대기 |
|---:|---:|---:|---:|
| 0 | 2 | 약 81.8ms | 82ms |
| 1 | 1 | 약 0.001ms | 0ms |
| 2 | 1 | 약 0.001ms | 0ms |
| 3 | 1 | 약 0.001ms | 0ms |

이것은 실제 게임 부하 결과가 아니라 계측기와 기존 정책의 동작을 확인하는 테스트다.
한 Worker의 작업이 길면 다른 Worker가 비어 있어도 그 Worker 뒤의 작업은 기다릴 수 있다.
이를 피하는 스케줄링으로 바꾸지는 않았다.

## 실제 Object 예제 조건

같은 Release 실행 파일에서 stride 0/256만 바꿔 대조했다.
Actor 7만·14만, 각 20초씩 2회, 첫 회 OFF→ON, 다음 회 ON→OFF다.
7만은 맵 320×320·이동 시도 2,000회/초, 14만은 453×453·4,000회/초다.
5초 분산 입장·1ms 입장 확인, seed 42, 추가 연산 0, 고정 50ms 예약,
5ms·256슬롯·poll·Task 통계 ON을 유지했다.
Actor 제출 표본 및 상세 타이머 추적은 둘 다 OFF다.
타이머 Worker 8개와 Dispatcher Worker 8개, 논리 CPU 8개 환경이다.

실제 예제는 균일한 가벼운 Actor 갱신이며 빈번한 Actor 간 상호작용 부하가 없다.
누적 지표만으로 순간적인 모든 편중이나 다른 게임 부하를 배제할 수 없다.

## 최종 측정 결과

통계 블록을 분리한 최종 빌드의 계측 ON 결과다.
시간/대기 범위는 각 실행 안의 Worker 최솟값~최댓값이며 서로 다른 실행을 합친 분포가 아니다.
건수는 round-robin 배정 자체를 확인하는 지표이고, 처리 시간과 함께 판단한다.

### 판단

전달 건수는 매우 균등했고 실제 내부 Task 수도 이번 예제에서는 균등했다.
그러나 14만 두 번째 실행의 최대 batch 시간은 평균보다 약 11.6%, 최솟값보다 약 23.4% 컸다.
건수 균등이 곧 실행 시간·큐 대기 균등을 뜻하지 않는다는 점이 확인됐다.
한두 Worker가 대부분의 작업을 처리하고 나머지가 계속 비는 극단적인 누적 편중은 관측하지 못했다.
현재 FPS 미달의 주원인이 특정 Dispatcher Worker로의 지속적인 집중이라는 증거는 부족하다.

이것은 순간적인 편중이 전혀 없다는 증명은 아니다.
OS 실행 배정·잠금/할당 대기 등이 batch 벽시계에 섞이므로 시간 차이의 CPU 원인은 확인 불가다.
긴 작업에서 round-robin이 대기를 만들 수 있다는 사실은 강제 불균형 테스트에서 별도로 확인했다.

## 계측 영향 대조

| Actor / 회차 | OFF FPS | ON FPS | OFF CPU | ON CPU |
|---|---:|---:|---:|---:|
| 7만 / 1 | 19.688 | 19.495 | 87.48% | 85.79% |
| 7만 / 2 | 19.027 | 19.627 | 81.57% | 88.07% |
| 14만 / 1 | 17.713 | 17.979 | 92.06% | 92.57% |
| 14만 / 2 | 18.114 | 17.982 | 93.09% | 92.56% |

최종 ON/OFF 대조에서 일관된 FPS 저하를 보이지 않았지만 환경 변동과 각 2회라는 제한 때문에
정확한 계측 비용 비율을 확정하지 않는다. 계측이 성능을 개선했다고 해석하지도 않는다.
처음 WorkerState 내부에 통계를 둔 시험은 14만 ON에서 14.437/17.380FPS로 편차가 컸다.
측정 간섭 가능성을 줄이려고 통계 저장 공간을 분리했으며 이 배치가 편차 원인이었다고 확정하지 않는다.
기본값은 계측 OFF로 유지했다.

최초 시험 8회와 최종 시험 8회 모두 종료 코드 0, 중복·미갱신 Actor·잔여 Task 0이었다.
계측 ON의 Worker별 전달/내부 Task·표본 합계는 전체 합계와 일치했다.
Release/Debug 솔루션 빌드와 실제 Worker 집계, 4개 생산자의 직렬화·정확한 배정/표본 건수,
이중 shutdown, 종료 전 조회 거부, 종료 후 제출 거부·소유권 정리 검사를 통과했다.

## 실행과 자료

```powershell
# 마지막 인수가 Dispatcher 표본 stride. 직전 0은 Actor 표본 OFF.
.\Source\x64\Release\AreaUpdateExample.exe 20 140000 4000 42 5000 1 0 453 job 0 poll 0 256
# 보존한 실행 파일로 새 결과 폴더에서 비교
.\Run-DispatcherBalance.ps1 -OutputDirectory artifacts/dispatcher-balance-repeat
```

artifacts/dispatcher-balance/isolated에 최종 실행 파일·핵심 소스를 보존한다.
measurements-isolated/results.csv는 실행별 요약이며, 각 실행의 dispatcher-workers.csv에는 실제 Worker별 상세 통계가 있다.
처음 통계를 WorkerState 내부에 둔 시험은 profiled/measurements에 별도로 보존하며 최종 집계와 섞지 않는다.
runtime.log와 CPU samples.csv, summary.json, 환경·해시·메모리 안전 계획도 보관한다.
tests의 self-test 로그에는 강제 불균형과 소유권·직렬 실행·종료 검사가 있다.
