# Area 큐 지연 분해와 파티션 처리량

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

후속 적응형 입장 정책과 비교 결과는 [적응형 스케줄링](AREA-ADAPTIVE-RESULTS.md)에 정리했다.
아래는 기존 고정 8회 정책을 계측한 기록이다.

## 범위

기존 선택형 계측을 확장했다. 스케줄링 정책·반경·batch 64·누적 입장 예산 8·공평성은 변경하지 않았다.
기본 계측은 OFF다. Area에 상시 시간 필드를 추가하지 않는다.
집계는 모든 batch/완료된 파티션 방문에 대해 수행하고 지연은 좌표 해시로 약 1/64 Area를 표본 추출한다.

## 지연 구간

| 지표 | 구간 |
|---|---|
| enqueue_ns | 타이머 콜백 시작→큐 push 반환 직후 |
| enqueue_profile_lock_ns | 위 구간 중 계측용 partition 잠금 획득까지. 별도 참고값이며 합계에 더하지 않음 |
| queue_residence_ns | 큐 등록 직후→batch pop 완료 직후 |
| extracted_to_run_ns | batch pop 완료→해당 Area::update 진입 직전 |
| ready_to_run_ns | 위 3개 구간의 합 |

등록 시각은 queue 잠금 해제 후 첫 clock 읽기이며 정확한 게시 명령 시각은 아니다.
표본은 계측용 partition 잠금을 유지한 채 등록 시각까지 기록하므로 추출이 먼저 진행할 수 없다.
추출 시각은 pop과 ready 카운터 감소 직후이며 해당 batch의 표본들이 같은 시각을 사용한다.
추출 이후에는 표본 stamp 갱신/조회·앞선 Area 갱신·lock 해제·OS 스케줄링 비용이 포함된다.
queue residence는 순수 파티션 차례 대기만이 아니라 admission 잠금·큐 추출 비용도 포함한다.
enqueue에는 기존에 없던 계측용 잠금과 map 접근 비용이 포함되므로 제품 경로의 잠금 비용으로 단정하지 않는다.
등록 후 wake_workers 비용은 등록 구간에 포함하지 않으며 소비자 실행과 겹칠 수 있다.
세 구간은 같은 타이머 표본에 대해 수집한다. 최초 활성화는 지연 통계에서 제외한다.

## 파티션 방문

하나의 방문(epoch)은 첫 입장 시도부터 마지막 runner의 leave에서 회전을 결정할 때까지다.
아래 집계는 완료된 방문에만 포함한다. 종료 당시 미완료 방문의 batch는 batch 통계에는 있지만 방문 통계에는 없다.

| 지표 | 의미 |
|---|---|
| epoch_areas | 방문 동안 꺼내서 처리한 Area 수. inactive skip도 포함 |
| epoch_admissions | 비어 있는 추출을 포함한 누적 입장 횟수. 최대 8 |
| epoch_remaining_areas | 회전 결정 시 해당 파티션 큐 길이의 atomic snapshot. 동시 enqueue로 변할 수 있음 |
| epoch_ns | 첫 입장부터 마지막 leave 통계 처리 진입까지. 마지막 계측 집계 비용은 제외 |
| budget_exhausted_epochs | 8회 예산을 모두 소비하고 회전한 방문 수 |
| budget_backlog_epochs | 예산 소진 + 회전 시 잔여 큐 존재인 방문 수 |
| backlog_epoch_areas/ns | 위 backlog 방문만의 처리량과 시간 분포 |

`area-partitions.csv`에 파티션별 모든 완료 방문·입장·Area·잔여 큐·소요 시간 합계를 기록한다.
`area-epochs.csv`에는 256번째 방문마다 한 건씩 최대 4,096건의 원시 표본을 보존한다.
제한을 넘긴 원시 표본은 epoch_samples_dropped로 표시하며 전체 집계는 계속 유지한다.
모든 방문을 원시 로그로 출력하지 않아 출력량과 메모리를 제한한다.

예산 소진 후 잔여 작업이 많으면 예산 압력을 관측할 수 있지만,
예산을 늘렸을 때의 FPS나 다른 파티션의 최대 대기 시간은 이 실험만으로 확인 불가다.

## 조건과 재현

Release x64, signal, 고정 50ms, Worker 8개, Task 통계 ON, 타이머 5ms/256슬롯이다.
추가 Actor 연산 0, seed 42, 5초 분산 입장/1ms 확인으로 이전과 같다.
28만은 맵 한 변 640/초당 이동 시도 8천, 14만은 453/4천이다.
실행 중 다른 빌드·분석 작업을 병행하지 않는다. 다른 시스템 프로세스까지 통제한 것은 아니다.

```powershell
.\tools\profiling\Run-AreaProfile.ps1 -Suite queue -OutputDirectory artifacts/area-queue-profile-repeat
.\tools\analysis\Analyze-AreaProfile.ps1 -InputDirectory artifacts/area-queue-profile-repeat
```

측정 파일은 `artifacts/area-queue-profile`에 보존한다. 6초 이후 1초 구간들을 합산해 분석한다.
초별 p99 상한은 전체 구간의 p99가 아니며 분포 bucket은 이전과 같은 2의 거듭제곱이다.

## 지연 분해 결과

아래는 6~20초 구간의 표본 가중 평균이다. 28만은 60초 ON 실행, 14만은 20초 ON 실행이다.

| 구간 | 14만 Actor | 28만 Actor |
|---|---:|---:|
| 콜백→큐 등록 | 0.00622ms | 0.00633ms |
| 큐 등록→batch 추출 | 7.11115ms | 64.82404ms |
| 추출→Area 진입 | 0.05546ms | 0.06085ms |
| 콜백→Area 진입 합계 | 7.17283ms | 64.89122ms |
| 등록 중 계측용 잠금 획득 대기(참고) | 0.00560ms | 0.00557ms |

28만 지연 표본은 463,852개, 14만은 447,446개다.
28만 콜백 이후 지연의 약 99.90%는 큐 등록 후 추출 전이다.
등록 지연 대부분은 계측용 잠금 획득 구간이지만 절대값은 평균 약 6µs로 작다.
계측 ON 경로의 이 잠금 대기를 OFF 제품 경로의 enqueue 잠금 비용이라고 해석하지 않는다.

28만 20초 반복에서도 큐 체류 평균 62.71ms와 68.99ms로 같은 양상이 관측됐다.
60초 실행의 20~40초는 88.84ms, 40~60초는 69.98ms였다.
등록/추출 이후 지연은 각각 약 6~9µs/60~71µs로, 평균 지연의 큰 부분이 아니다.
따라서 이 계측 조건에서 우선 볼 위치는 등록 함수나 batch 내부 Actor 갱신보다
등록된 Area를 다음 batch로 받아들이는 스케줄링 경로다.

## 파티션 예산 압력

| 실행/구간 | 완료 방문 | 방문당 Area | 방문당 입장 | 회전 시 평균 잔여 Area | 예산 소진+잔여 큐 비율 |
|---|---:|---:|---:|---:|---:|
| 14만 20초/6~20초 | 61,993 | 458.10 | 7.80 | 362.05 | 73.86% |
| 28만 60초/6~20초 | 57,789 | 512.00 | 8.00 | 5,217.24 | 100% |
| 28만 60초/20~40초 | 67,217 | 512.00 | 8.00 | 5,835.49 | 100% |
| 28만 60초/40~60초 | 79,014 | 512.00 | 8.00 | 5,385.21 | 100% |

28만의 두 20초 ON 반복에서도 6~20초의 해당 비율은 모두 100%, 처리량은 방문당 512개였다.
즉, 이 부하에서 빈 추출이나 덜 찬 batch가 입장 예산을 낭비하는 현상은 주된 관측 문제가 아니다.
예산을 꽉 채워 처리해도 잔여 작업을 남긴 채 다른 파티션으로 회전한다.
60초 전체 파티션별 완료 방문 수는 9,405~9,406회로 순회가 특정 파티션에 편중된 증거는 없다.
전체 최대 잔여 큐는 한 파티션에서 7,754개였다.

28만 6~20초에 방문 완료율은 초당 약 4,128회, 25개 파티션을 도는 평균 순회 주기는 약 6.06ms다.
평균 잔여 5,217개는 512개 묶음 약 10.2회 분량이다.
단순 근사로 10.2회×6.06ms≈61.7ms이며 관측 큐 체류 64.8ms와 비슷한 규모다.
FIFO 위치·동시 유입·구간 경계가 달라 정확한 대기 시간 공식이나 인과관계 증명은 아니다.
실제 완료 방문 처리량은 같은 구간 초당 약 211만 Area였다.

## 계측 영향과 한계

| 실행 | 계측 | 전체 평균 FPS | 안정 구간 CPU |
|---|---|---:|---:|
| 28만 60초 | OFF | 12.418 | 65.77% |
| 28만 60초 | ON | 9.717 | 59.85% |
| 28만 20초 | ON | 11.093 | 62.97% |
| 28만 20초 반복 | ON | 10.840 | 58.59% |
| 14만 20초 | ON | 20.005 | 54.91% |

60초 쌍에서 ON의 FPS가 약 21.8% 낮았다. 시간대별 변동을 분리한 다회 무작위 실험은 아니므로
순수 계측 비용이 정확히 21.8%라고 단정할 수는 없다. 확장 계측은 잠금 안의 stamp 갱신과
분포 집계 비용을 더하므로 병목의 세기를 과장할 수 있다.
OFF 제품 실행에서도 잔여 큐가 5천 개이거나 예산 압력이 100%라고 확정할 수 없다.
이 수치로 제품의 절대 처리량이나 예산 변경 후 성능을 예측하지 않는다.

참고로 OFF의 기존 누적 카운터에서도 전체 실행 평균은 방문당 488.66 Area/7.71 입장,
입장당 63.35 Area였다. 초기 입장·빈 방문·종료 시 미완료 방문이 포함된 값이며,
계측 ON의 안정 구간 집계와 직접 비교할 수는 없다. 예산 가까이 처리하는 양상은 보이지만
OFF의 잔여 큐 비율은 기존 카운터만으로 확인 불가다.

확인된 것은 ON 반복들에서 큐 체류가 지연의 대부분이며, 예산을 꽉 쓰고도 잔여 큐를 남긴다는 점이다.
예산을 무조건 늘리는 것이 정답이라는 뜻은 아니다. 다음 개선 실험은 회전/장벽의 고정 비용을 줄이는 쪽과
공평성을 명시적으로 제한한 적응형 입장 예산을 분리 비교할 근거가 있다.
이번 작업에서는 둘 다 적용하지 않았다.

## 검증

Release/Debug MSBuild, AreaTests, UpdateComparison --test, 서식·명명 검사가 통과했다.
회귀 검사와 모든 측정에서 지연 합계 일치 및 방문/파티션 집계 합계 일치를 확인했다.
1,024개 Area 대기 테스트에서도 예산 소진·512개 처리·잔여 큐가 계측됐으며 기존 공평성 검사는 유지됐다.
모든 실행은 Task 수명 검증을 통과했고 미갱신 Actor·중복 갱신·종료 코드는 0이었다.
