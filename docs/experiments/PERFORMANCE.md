# 초기 AreaUpdate 측정 기록

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 재현

이 문서는 초기 우선순위 heap·폴링 런타임의 기록이다. 이후 Worker·타이머 휠 변경과 별도 측정은
[실행 구조](../runtime.md)를 참고한다. 아래 수치는 현행 구현의 성능으로 해석하지 않는다.

Visual Studio MSBuild로 Release x64 솔루션을 빌드한다.

```powershell
& 'C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe' Source\AreaUpdate.sln /m /p:Configuration=Release /p:Platform=x64
.\Source\x64\Release\AreaTests.exe
.\Run-Measurements.ps1
```

당시 예제의 위치 인수:

```text
AreaUpdateExample.exe seconds actorCount movementAttemptsPerSecond seed
```

Run-Measurements.ps1은 Actor 1,000개/이동 초당 200회, Actor 10,000개/이동 초당 2,000회를
각 20초씩 세 번 실행하고 Actor 5,000개/이동 초당 20,000회를 600초 실행한다.
seed 42, Worker 8개, 파티션 25개, Area 102,400개로 순차 실행했다.
이동은 초마다 한꺼번에 시도하며 모든 시도가 성공하는 것은 아니다.

프로세스 출력·1초 간격 자원 표본·집계 CSV는 artifacts/measurements/에 저장한다.
실행 시간에 60초를 더한 감시 제한을 적용하며 종료 코드가 0이 아니면 거부한다.

## 지표와 한계

- Actor FPS = 전체 갱신 수 / 측정 시간 / Actor 수.
- CPU 100%는 논리 CPU 하나를 완전히 사용한다는 뜻이다. 이 장비에서는 8로 나누면 전체 용량 대비 비율이다.
- 메모리는 약 1초마다 표본 수집한 프로세스 private bytes다.
- 갱신 간격은 10ms 버킷이다. 80은 [80, 90)ms이며 마지막 [1000ms, 무한대) 버킷은 정확한 백분위가 아니다.
- 같은 Actor 동시 호출은 중복 카운터를 올리고 종료 시 실패한다. 한 번도 갱신되지 않은 Actor도 실패다.
- 계측과 atomic 카운터 비용이 포함되며 나머지 콜백에는 게임·네트워크·DB 로직이 없다.
- 중복 0이 모든 데이터 경쟁·수명 오류·공간 겹침의 부재를 증명하지 않는다. sanitizer 검사가 아니다.
- 미갱신 카운트는 최초 실행만 검사한다. 마지막 갱신 이후의 종료 직전 정체는 완료 간격 지표에 포함하지 않는다.
- 당시 동등한 원본 radius-lock 기준을 측정하지 않아 원본 대비 성능 유지율을 결론 내릴 수 없었다.

## 환경

- AMD Ryzen 5 3400G, 4코어/논리 프로세서 8개.
- Windows 빌드 26200.
- Visual Studio 18 Community, MSBuild 18.11.1, MSVC v145.
- 사용 중인 대화형 장비에서 측정해 다른 시스템 활동을 통제하지 않았다.
  제한된 환경의 첫 빌드는 PDB 오류가 있었으며 같은 솔루션을 일반 환경에서 성공적으로 빌드했다.
- 실행 파일 SHA256: F4F334442300C458189FB451C2E7CDE1FDB8ED8931481B6B3ECC26229AE98066.

## 결과

짧은 부하별 순차 실행 3회의 결과다.

| Actor | 이동 시도/초 | 평균 Actor FPS | FPS 범위 | 평균 CPU, 논리 CPU 하나=100% | 최대 private MB |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 200 | 16.46 | 16.085-16.823 | 4.03% | 38.18 |
| 10,000 | 2,000 | 15.28 | 15.055-15.613 | 15.65% | 52.75 |

6회 모두 정상 종료했고 관측된 Actor 중복 갱신과 최초 미갱신은 0이었다.
최대 갱신 간격은 132~178ms, P99 버킷은 드문 배치의 2회차(90ms)를 제외하면 80ms였다.
전체 CPU 부하가 낮아도 설정한 20FPS를 달성하지 못했다. 큐 회전·Worker 폴링/대기·완료 후 50ms
재예약이 지연 후보지만 이 실행에서는 개별 기여를 분리하지 않았다.

감시 시간 초과와 중복 실행 없이 완료했다. 메모리는 최초 표본보다 약 6.07MB 증가했고 끝부분에도
완만하게 증가했다. 이동하면서 방문한 Area의 Actor·pending 목록 용량이나 할당기 보유 메모리가
후보지만 할당 프로파일을 수집하지 않았으므로 메모리 누수가 없다고 입증한 것은 아니다.

## 당시 후속 과제

1. Worker 폴링·대기, 파티션 입장·회전, 타이머 만료를 추적해 20FPS 미달 원인을 확인한다.
2. 살아 있는 할당 수나 heap 스냅샷으로 vector·타이머 보유 용량과 누수를 구분한다.
3. 스케줄러의 완전한 정확성이나 야간 장시간 검증을 주장하기 전에 공간 중복과 종료 직전 정체를 계측한다.

측정 전 Release 회귀 테스트도 통과했다. 10분 스트레스 시험이며 야간 장시간 시험이나 실제 게임 부하는
아니다. 실행 도구와 원본 CSV·로그를 사용하면 기간을 바꾸어 재현할 수 있다.
