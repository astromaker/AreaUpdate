## 시험 조건

- 시나리오: [../testing.md](../testing.md). 총 13개, 방식별 3회, 합계 78회 실행.
- Windows 10.0.26200, 논리 프로세서 8개, MSBuild 솔루션 x64 Release 빌드.
- 동일 seed 42, 측정 100 tick, 별도 World에서 준비 실행 5 tick. 각 방식은 별도 프로세스에서 실행.
- 아래 시간은 3회 중앙값. 배율은 Job 시간 / Area 시간으로, 1보다 크면 Area가 빠름.
- 측정 바이너리 SHA256: `123BC2E33BF24D3A2283A92F94F9A575EC0502E376F84C12B7296197DCA9476D`.

중요: Area 비교 모드는 실제 `Area::update()`를 호출하지만, tick별 25개 partition barrier를 사용하는 **비교용 스케줄러**다. 운영 `AreaExecuter`의 비동기 타이머 실행기 전체 성능을 직접 비교한 결과는 아니다. 두 방식 모두 고정 위치, 동일 연산, 반경 2의 가산형 damage 이벤트를 사용한다. 이동 비용과 대상 상태에 의존하는 복잡한 상호작용은 이 수치에 포함되지 않는다.

## 해석

- 낮은 연산량에서는 이번 조건 전체에서 Area가 1.65~4.97배 빨랐다. 특히 S05의 높은 상호작용 조건에서는 4.07배였다.
- 독립 연산량이 커지면 Job이 유리했다. S10은 Job이 2.72배, 한 Area에 집중한 S11은 4.88배 빨랐다.
- Worker 1개에서 8개로 늘릴 때 무거운 연산의 속도 향상은 Job 5.04배, Area 1.80배였다.
- 현재 비교용 Area 스케줄러는 64개 Area를 한 작업으로 묶는다. 중앙 64×64 배치와 5×5 coloring에서는 partition당 최대 169개 Area이므로 병렬 작업은 최대 3개뿐이다. 실제 점유 상태에 따라 더 적다. Worker 4~8개의 정체에는 이 작업 분할 제한이 있으며, Area 설계 전체의 본질적 한계라고 단정할 수 없다.
- 한 Area에 Actor가 몰리면 그 Area의 Actor 업데이트는 직렬이다. 반면 Job 모드는 Actor별 독립 작업을 분산할 수 있다.

## CPU와 메모리

- S05의 측정 구간 프로세스 CPU 시간 중앙값은 Job 12.516초, Area 1.281초였다. 대기시간을 포함한 경과시간과는 다른 지표다.
- S10은 Job CPU 21.625초, Area 16.656초였다. Job은 더 많은 CPU를 병렬로 사용하면서 경과시간을 줄였다.
- S04의 샘플링된 peak private memory 중앙값은 Job 7.16MiB, Area 37.75MiB였다. 다만 Area는 전체 102,400개 Area를 보유하고 Job은 미리 계산한 이웃 목록을 이용하므로, 동등한 운영 AOI 시스템의 메모리 비교가 아니다.
- 메모리 샘플은 초기화·준비 실행·검증도 포함하며, 짧은 peak는 놓칠 수 있다. CPU 시간은 측정 실행 구간만 포함한다.

## 정확성 및 실제 런타임

- 78회 모두 Actor별 업데이트 수와 수신 damage 검증을 통과했고, 대응하는 두 방식의 checksum 및 생성 이벤트 수가 일치했다. 동시 접근 위반은 합계 0건이었다.
- 이벤트 수 출력은 생성 입력 수이며 독립적인 전달 횟수 계측값은 아니다. 전달 결과는 Actor별 damage 합으로 검증했다.
- 최종 솔루션 Release 빌드 성공, Release / Debug `AreaTests.exe` 모두 종료 코드 0. 종료 중 제출, partition 배타성, 병렬 batch 진행, 타이머 및 Area 멤버십 테스트 포함.
- 실제 `AreaUpdate.exe 30 10000 2000 42` 통합시험: 30.233초, 이동 48,868회, 업데이트 5,646,344회, Actor 평균 18.676 FPS.
- 실제 런타임 중복 업데이트 0, 미실행 Actor 0, 종료 후 pending Task 0, live Task 0. 최대 업데이트 간격 112ms, p99 구간 50ms. 생성/파괴 Task 모두 5,389,047개였다.

## 결론과 다음 측정

빈번한 단순 상호작용의 처리 비용을 줄이려는 AreaUpdate의 목적에는 유효한 결과다. 다만 무거운 Actor 연산과 공간 집중에서는 Actor Job이 우세했다. 다음 우선순위는 Area batch 크기를 8/16/32/64로 바꾸어 확장성 정체를 분리 측정하는 것이다. 이후 이동·동적 이웃 갱신·대상 상태 조회를 두 모델에 동등하게 추가하고 운영 실행기까지 비교해야 한다.

이번 결과는 조건당 3회 측정이며 통계적 유의성을 보장하지 않는다. 수치는 현재 구현과 입력 조건에 한정한다.
