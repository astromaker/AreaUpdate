# Area 병목 계측

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

후속 큐 지연 분해·파티션 처리량은 [상세 계측](AREA-QUEUE-PROFILE-RESULTS.md)에 정리했다.

## 목적과 조건

batch 부하 편차, 타이머/실행 대기 분리, 20초와 60초의 시간 추이를 확인한다.
실행 정책을 바꾸는 작업이 아니라 선택형 계측이다. 기본값은 OFF다.

예제 마지막 인수 `areaProfileStride` 또는 측정 스크립트의 `-AreaProfileStride 64`로 활성화한다.
좌표 해시로 약 1/64 Area를 골라 반복 관찰하며 매 64번째 update를 뽑는 방식은 아니다.
모든 비어 있지 않은 batch의 시간과 부하량은 기록한다.
계측은 별도 통계 상태와 잠금을 사용하므로 ON/OFF 결과를 구분한다.
Area에 상시 시간 필드를 추가하거나 매 tick 전체 Area를 스캔하지 않는다.
단, 계측 ON인 예제 main은 초당 한 번 Actor/Area를 읽어 추이를 기록한다.

공통 조건은 Release x64, Core Worker 8개, signal, 고정 50ms 예약,
Task 통계 ON, 5ms/256슬롯 타이머, seed 42, 5초 분산 입장/1ms 확인, 추가 연산 0이다.
28만 Actor는 맵 한 변 640/이동 시도 초당 8천, 14만은 453/4천이다.
타이머 상세 추적·Object/Dispatcher 프로파일은 OFF다.

## 지표 정의

| 지표 | 의미 |
|---|---|
| batch_ns | 큐 추출 후 batch 갱신과 재예약 시간. 계측 자체 비용 포함. 빈 batch는 제외 |
| batch_areas | 비어 있지 않은 batch의 Area 수 |
| batch_actor_reservations | batch 시작 시 Area의 Actor 예약 수 합. pending 포함, 실제 update 호출 수 아님 |
| timer_late_ns | 원래 예약 deadline부터 타이머 콜백 시작까지. 휠 반올림·Worker 스케줄링·앞선 콜백 비용 포함 |
| ready_to_run_ns | 콜백 시작부터 해당 Area update 직전까지. enqueue·partition 대기·앞선 batch 항목·계측 비용 포함 |
| deadline_to_run_ns | 위 두 지연의 합. 최초 활성화는 타이머가 아니므로 세 지연 표본에서 제외 |
| epoch_tail_ns | 같은 partition 방문에서 첫 비어 있지 않은 batch 완료부터 마지막 leave까지의 간격 |
| blocked_return_ns | idle_state에서 ready 작업+입장 예산 소진을 관측한 시점부터 그 Worker의 다음 on_tick 입장 시도까지 |

epoch_tail은 실제 Worker 유휴 시간 합이 아니다. 순차 추가 입장과 leave 잠금 비용도 포함한다.
blocked_return도 순수 장벽 수면 시간이 아니다. OS 기상 지연과 다음 루프의 타이머 처리를 포함하며,
종료 시 아직 복귀하지 않은 구간은 포함하지 않는다. 이 둘을 CPU 대기율로 변환하지 않는다.
갱신 시작은 Area::update 진입 직전이며 진입 후 inactive 검사로 반환하는 경우도 포함한다.

분포는 2의 거듭제곱 bucket이다. p50/p95/p99는 bucket 상한이며 정밀 분위수가 아니다.
최대 bucket은 실제 관측 최댓값으로 표시한다. 초별 p99로 전체 p99를 재구성할 수 없다.
각 profile 행은 batch/복귀 완료 시각의 1초 구간으로 귀속되므로 경계를 넘는 작업을 분할하지 않는다.

`AREA_SECOND`는 약 1초 간격으로 Actor update 원자 카운터를 합산해 증가량을 구한다.
분모는 Actor별 입장 후 시간 합계의 증가량이므로 입장 중에도 Actor 노출 시간을 반영한다.
동시 갱신 중 읽는 근사 snapshot이다. 활성 Area 수도 원자 상태를 순차 읽은 근사값이다.
마지막 부분 구간은 전체 SUMMARY에는 포함되지만 초별 main 출력에는 없을 수 있다.

## 재현과 자료

```powershell
.\tools\profiling\Run-AreaProfile.ps1 -OutputDirectory artifacts/area-profile-repeat
.\tools\analysis\Analyze-AreaProfile.ps1 -InputDirectory artifacts/area-profile-repeat
```

실행 순서와 설정은 `artifacts/area-profile/plan.csv`, 실행별 요약은 `results.csv`에 보존한다.
각 폴더에 실행 로그, CPU 표본, area-profile.csv, area-profile-seconds.csv,
area-seconds.csv가 있다. OFF 실행에는 Area profile CSV가 생성되지 않는다.
분석 스크립트는 첫 6초 이후 구간을 합산하고 초별 FPS 추이를 별도 CSV로 모은다.

## 실행 결과와 계측 영향

| Actor/실행 | 계측 | 평균 FPS | 안정 구간 CPU |
|---|---|---:|---:|
| 28만/20초 | OFF | 10.764 | 58.74% |
| 28만/20초 | ON | 12.248 | 68.25% |
| 28만/20초 재실행 | ON | 12.417 | 66.77% |
| 28만/60초 | ON | 10.580 | 61.26% |
| 28만/60초 | OFF | 11.190 | 62.46% |
| 28만/60초 별도 분석 병행 없이 재실행 | ON | 11.901 | 66.39% |
| 28만/60초 별도 분석 병행 없이 재실행 | OFF | 12.943 | 69.17% |
| 14만/20초 | ON | 19.895 | 54.81% |

마지막 60초 ON/OFF 비교에서 ON의 FPS가 약 8.1% 낮았다. 앞선 60초 쌍에서는 약 5.5% 낮았다.
반면 20초에서는 ON이 높아 시간대별 변동과 계측으로 인한 실행 타이밍 변화가 관측된다.
무작위 다회 반복 실험은 아니므로 순수 계측 비용을 특정 비율로 확정할 수 없다.
계측 ON 결과를 OFF 성능으로 취급하지 않는다. 최초 60초 ON 실행 중 일부 결과 분석을 병행했으며,
환경 교란 가능성을 배제하지 않기 위해 분석을 병행하지 않은 60초 ON/OFF를 추가했다.
여기서 별도 분석 병행 없음은 다른 시스템 프로세스까지 통제했다는 뜻은 아니다.

## 1. Batch 편차와 장벽

아래는 추가 60초 ON 실행의 6~20초 구간이다. 평균은 관측 횟수로 가중했다.

| 지표 | 평균 | 최댓값 | 초별 p99 bucket 상한 범위 |
|---|---:|---:|---:|
| batch 처리 | 75.57µs | 5.85ms | 262.14µs |
| batch Area 수 | 약 64개 | 64개 | 64개 |
| batch Actor 예약 수 | 88.31개 | 125개 | 118~125개 |
| epoch 첫 완료→마지막 leave | 97.35µs | 5.88ms | 524.29~1,048.58µs |
| 입장 차단 관측→다음 입장 시도 | 97.49µs | 54.61ms | 524.29~1,048.58µs |

batch 수는 516,608개, 비어 있지 않은 epoch 표본은 64,576개다.
batch p99 상한은 평균의 약 3.5배이며 긴 꼬리는 존재한다.
다만 Actor 예약 수의 최댓값이 평균의 약 1.42배인 균일 예제이므로,
일부 Area에 Actor가 극단적으로 몰린 것이 주된 원인이라는 증거는 없다.
Actor 예약 수와 실행 시간의 batch별 상관계수는 수집하지 않아 인과관계는 확인 불가다.
장벽 관측 간격은 단일 batch 처리 시간과 비슷한 규모지만 이것만으로 순수 장벽 비용을 확정하지 않는다.
분포 상한을 평균하거나 전체 실행의 p99인 것처럼 표시하지 않았다.

## 3. 타이머와 실행 대기 분리

| 실행/구간 | deadline→콜백 평균 | 콜백→Area 진입 평균 | 합계 평균 |
|---|---:|---:|---:|
| 14만 20초/6~20초 | 4.22ms | 6.72ms | 10.94ms |
| 28만 60초 재실행/6~20초 | 3.06ms | 57.19ms | 60.26ms |
| 28만 60초 재실행/20~40초 | 3.00ms | 55.36ms | 58.36ms |
| 28만 60초 재실행/40~60초 | 3.04ms | 58.34ms | 61.38ms |

28만의 초반 안정 구간 지연 표본은 516,599개다. 평균 전체 지연의 약 94.9%가 콜백 이후에 있다.
다른 28만 20초 ON 실행에서도 콜백 전 3.18ms/후 55.40ms,
재실행에서도 콜백 전 3.02ms/후 56.61ms로 같은 방향이다.
따라서 이 부하에서 5ms 휠 해상도를 먼저 줄이는 것보다는
partition 대기·batch 진입·기상과 실행 큐 처리 경로를 우선 조사하는 것이 근거에 맞는다.
이 지연은 partition 순번 대기만을 독립 측정한 값이 아니므로 특정 함수 하나의 비용으로 단정하지 않는다.

## 4. 시간 추이

아래 FPS는 해당 구간에 보고된 초별 FPS를 보고 간격으로 가중한 값이며 SUMMARY 평균과 다르다.
profile 구간은 완료 시각 기준, main 보고 구간은 보고 끝 시각 기준이므로 정확한 경계는 일치하지 않는다.

| 28만 60초 재실행 | 초별 FPS 가중 평균 | 활성 Area 범위 | 콜백 후 실행 대기 | epoch tail 평균 |
|---|---:|---:|---:|---:|
| 6~20초 | 11.631 | 202,798~203,065 | 57.19ms | 97.35µs |
| 20~40초 | 11.929 | 202,773~202,967 | 55.36ms | 92.27µs |
| 40~60초 | 11.531 | 202,763~203,035 | 58.34ms | 98.48µs |

이 재실행에서는 시간이 지날수록 일관되게 느려지는 현상이 재현되지 않았다.
활성 Area 수는 입장 완료 후 약 20.3만으로 안정적이었다.
앞선 60초 ON에서는 20~40초 FPS 9.132/실행 대기 83.31ms/epoch tail 148.17µs로 함께 악화됐으나,
분석 작업 및 OS 스케줄링 등 환경 변동을 배제할 수 없으므로 코드의 시간 경과 버그라고 확정하지 않는다.
실행 길이가 다르면 초기 입장 구간이 전체 FPS 평균에 차지하는 비중도 달라진다.

## 결론과 검증

28만에서 가장 큰 관측 지연은 타이머 발견 전이 아니라 콜백 이후 Area 실행 전이다.
균일 예제에서 심한 Actor 수 불균형의 증거는 약하며, 장벽/기상/큐 진입 비용 분리를 더 좁혀 볼 근거가 생겼다.
이번 작업에서 스케줄링 정책·공평성·공간 반경·batch 크기는 변경하지 않았다.

Release/Debug MSBuild, AreaTests, Release UpdateComparison --test,
tools/quality/Format-Code.ps1 -All -Check, tools/quality/Check-CodeStyle.ps1을 통과했다.
회귀 검사에서 histogram 경계/병합, OFF 상태, 타이머 표본 수, 최초 활성화 제외,
지연 합계 일관성을 확인했다. 모든 측정은 Task 수명 검증 통과, overlaps/미갱신 Actor/종료 코드 0이다.
