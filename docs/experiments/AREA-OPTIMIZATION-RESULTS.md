# Area 실행 경로 최적화

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 범위

signal 기본값 적용 직후 실행 파일을 기준으로 병목 후보를 독립 비교한다.
공간 반경, batch 64, 파티션당 누적 입장 예산 8, 파티션 순회와 마지막 runner 완료 장벽은 유지한다.
Actor 소유권, Object의 round-robin, 오브젝트 풀, idle Worker 관리/stealing은 변경하지 않는다.

## 변경 후보

1. 입장과 큐 추출을 같은 partition 잠금 경계로 묶는다.
   기존에는 입장 직후 여러 소비자가 큐 try_lock에 경합하고, 실패도 입장 예산을 소비했다.
   큐 추출까지만 직렬화하며 Area 갱신 자체는 잠금 밖에서 병렬 실행한다.
   기존에도 leave_partition에서 partition → queue 순으로 잠갔으며 이 순서를 유지한다.
   enqueue는 queue 잠금을 해제한 뒤 wake_workers의 partition 잠금을 획득한다.
2. 제외: 자신의 Worker에 타이머를 예약할 때 소유 타이머에 직접 등록하는 후보.
   외부 스레드는 기존 제출 큐를 사용한다. 즉시 작업도 기존 경로를 유지한다.
   접수 중/종료 거부/Task 수명/추적 시각/타이머 수량은 기존 방식으로 관리한다.
   직접 등록 타이머는 제출 큐에 들어가지 않으므로 queue depth에는 포함하지 않는다.
   두 번의 비교에서 FPS가 낮아져 실제 코드에는 반영하지 않았다.
3. 제외: wake_workers에서 남은 파티션 입장 예산만큼만 깨우는 후보.
   예산 소진 중인 파티션은 마지막 runner가 완료하고 회전해야 다시 실행 가능하다.
   마지막 runner의 회전 알림은 유지하고 실행 불가능한 중간 기상만 제한한다.
   대기 횟수 감소는 관측했지만 FPS 이득이 재현되지 않아 실제 코드에는 반영하지 않았다.

최종 제품 코드에는 1번만 반영한다. Core Worker의 동작은 변경 전과 같다.
자기 Worker 타이머 재예약 회귀 검사는 기존 경로에서도 유효하므로 유지한다.
공평성 검사는 같은 파티션에 1,024개 Area를 넣고 다음 파티션의 첫 실행 전 처리량이
8×64개 이하인지 확인하도록 강화했다.

## 후보 분리 실험

각 행의 FPS는 동일 조건 2회 실행의 중앙값(두 값의 평균)이다. 다른 행끼리는 실행 시간이 다르다.

| 비교 | 기준 FPS | 후보 FPS | 판단 |
|---|---:|---:|---|
| 입장·추출 통합 | 11.565 | 12.630 | 채택, 아래 최종 재측정 참고 |
| 통합 + 자기 Worker 타이머 직접 등록 | 12.820 | 11.700 | 제외 |
| 통합 + 입장 예산 기반 기상 제한 | 12.870 | 12.595 | 제외 |

입장·추출 통합의 기준 FPS 범위는 11.24~11.89, 후보는 12.21~13.05였다.
자기 타이머 직접 등록 후보의 범위는 11.46~11.94였다.
기상 제한은 기준 12.50~13.24, 후보 12.35~12.84로 차이가 작고 겹친다.
직접 등록 후보가 느려진 정확한 원인은 이번 측정만으로 확인 불가다.

## 최종 교차 비교

각 조건 20초씩 2회, 기존→후보→후보→기존 순이다. 2회 중앙값을 표기한다.

| Actor | 변경 전 FPS | 변경 후 FPS | 변경 전 CPU | 변경 후 CPU |
|---:|---:|---:|---:|---:|
| 140,000 | 19.763 | 20.001 | 52.06% | 51.45% |
| 280,000 | 11.514 | 13.000 | 62.55% | 65.47% |

14만 FPS 범위는 기존 19.522~20.004, 후보 19.994~20.007이다. 차이가 작다.
28만 FPS 범위는 기존 11.051~11.976, 후보 12.913~13.086이다.
28만 중앙값 기준 약 12.9% 개선됐으며, 대기 횟수는 680,017→513,125로 약 24.5% 줄었다.
입장 후 큐 잠금 실패로 예산을 낭비하는 경로는 제거했지만 28만에서 목표 20 FPS는 아직 미달이다.
CPU도 100%에 도달하지 않으므로 모든 스케줄링 병목이 해결됐다고 볼 수 없다.
잠금 경합/빈 batch/OS 기상 비용 각각의 기여 비율은 확인 불가다.
서로 다른 파티션 동시 실행을 허용하거나 공평성 예산을 늘려 얻은 개선은 아니다.

`final/results.csv` 및 각 실행의 로그·요약·CPU 표본·실행 파일 해시를 보존했다.
`before/AreaUpdateExample.exe`는 signal 기본값 적용 직후 기준 실행 파일이며,
`candidate/AreaUpdateExample.exe`는 입장·추출 통합만 적용한 비교 실행 파일이다.
마지막 회귀 테스트 강화 후 다시 빌드한 실행 파일은 별도 `validated` 폴더에 보존한다.

## 지속 부하 확인

동일 28만 조건을 60초로 늘려 각 버전 1회 실행했다. 후보를 먼저, 기준을 나중에 실행했다.

| 버전 | 평균 Actor FPS | 안정 구간 CPU | 남은 Task | 미갱신 Actor | 종료 코드 |
|---|---:|---:|---:|---:|---:|
| 변경 전 | 11.203 | 63.19% | 0 | 0 | 0 |
| 변경 후 | 11.475 | 62.42% | 0 | 0 | 0 |

60초 비교의 FPS 개선은 약 2.4%다. 두 버전 모두 Task 생성/소멸 검증을 통과했다.
20초 결과의 12.9% 이득을 지속 부하 전체로 일반화하지 않는다.
길이에 따른 성능 변화의 정확한 원인은 확인 불가다. CPU 실행 프로파일 없이
타이머 위상 변화, OS 스케줄링, 열/주파수 변화 중 하나로 단정할 수 없다.
이 검사는 60초 지속 부하이며 장시간 안정성 검증을 대체하지 않는다.

## 남은 병목

후속 batch·지연·시간 추이 계측은 [Area 병목 계측](AREA-PROFILE-RESULTS.md)에 별도로 정리했다.

누적 입장 8회 후 마지막 runner까지 기다리는 장벽은 여전히 존재한다.
28만에서 CPU 여유가 남으므로 실행 가능 작업과 기상/실행 장벽을 더 분리 계측할 여지가 있다.
장벽을 무작정 제거하면 공간 충돌 안전성을 잃으므로 이번에는 변경하지 않았다.
이번 결과는 최대 성능 달성 선언이 아니라, 측정으로 확인한 한 단계의 개선이다.

Release/Debug 솔루션 빌드, AreaTests, UpdateComparison --test,
tools/quality/Format-Code.ps1 -All -Check, tools/quality/Check-CodeStyle.ps1을 통과했다.
수정 C++ 파일의 UTF-8 BOM과 CRLF를 확인했다.

## 측정 방식

Release x64, Task 통계 ON, signal, 고정 50ms, 타이머 5ms/256슬롯이다.
28만 Actor, 맵 한 변 640, 초당 이동 시도 8천, 5초 분산 입장/1ms 확인,
추가 Actor 연산 0, 실행당 20초로 비교한다. CPU는 입장 완료 후 안정 구간 기준이다.
기존→후보→후보→기존 순서로 교차 비교하며 실행 파일을 별도로 보존한다.
평균 Actor FPS와 전체 논리 CPU 대비 사용률을 함께 본다.

자료는 `artifacts/area-admission-optimization`에 보존한다.
결과가 개선되더라도 빈번한 상호작용이나 집중 배치에서의 일반적 우위를 뜻하지 않는다.
실제 잠금 경합 시간은 계측하지 않았으므로 시간 기여 비율은 확인 불가다.
