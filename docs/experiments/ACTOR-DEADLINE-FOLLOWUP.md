# Actor deadline 수정 후 검증과 대기 분해

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 결론

이동 중 갱신이 계속 사라지던 경로의 수정은 장시간 검사에서도 유지됐다. 그러나 28만 Actor 과부하에서는 20FPS에 도달하지 못했고, Actor별 deadline을 유지하면서 타이머 Task 묶음 효율이 나빠진 비용도 확인했다.

대기는 주로 큐 게시 이후 첫 실행 시도 전 구간이었다. 목적지 예약을 앞당겨 Task를 더 만드는 변경은 적용하지 않았다. 대신 동일한 deadline의 예약을 묶음 안에서 모아 Task 생성 수를 줄이는 변경을 적용했다. Actor deadline, 반경 잠금, 큐 선두 실패 시 중단, batch 64, partition 공평성 정책은 유지했다.

## 1. 계측 전 재검증

Release x64, Task 통계 ON, Worker 8개, signal 대기, 5천 Actor, seed 42다. 서로 다른 사례는 순차 실행했다. 이 단계는 Actor deadline 수정 후이지만 이번 계측 및 예약 정렬을 적용하기 전 실행 파일로 수행했다.

| 모델 / 부하 / 배치 | 길이 | 정상 구간 FPS | p99 상계 | 관측 최대 간격 |
|---|---:|---:|---:|---:|
| radius / synthetic / 균등 | 300초 | 19.999 | 70ms | 159ms |
| radius / synthetic / 경계 | 300초 | 20.001 | 70ms | 81ms |
| partition / synthetic / 균등 | 60초 | 20.003 | 70ms | 103ms |
| partition / synthetic / 경계 | 60초 | 19.999 | 70ms | 71ms |
| radius / verify / 균등 | 60초 | 20.003 | 70ms | 70ms |
| radius / verify / 경계 | 60초 | 20.001 | 70ms | 69ms |
| partition / verify / 균등 | 60초 | 19.998 | 70ms | 114ms |
| partition / verify / 경계 | 60초 | 19.997 | 70ms | 69ms |

총 16분은 여러 프로세스 실행의 합계이며 하나의 프로세스를 16분 실행한 결과는 아니다. 8회 모두 이벤트 생성/적용 건수가 일치했고 합계 18,384,427건이었다. synthetic은 전체 수신자 ID를 보관하지 않으며, verify 4회의 2,819,744건은 수신자별 ID 전체와 피해 합계까지 검증했다. 모두 overlap 0, 종료 live Task 0, verify 소유권 왕복 검사 성공이었다.

radius synthetic의 private memory 30~60초 평균 → 마지막 30초 평균은 균등 11.763 → 11.992MiB, 경계 10.739 → 10.879MiB였다. 이 관측은 무누수 증명이 아니다. 60초 사례는 두 집계 구간이 겹치므로 메모리 장기 추세 판단에 사용하지 않았다. verify ID 기록에 의한 메모리 증가는 synthetic과 구분했다.

### 28만 Actor

640×640 맵, 초당 이동 시도 8,000, 입장 1초/1ms 간격, 각 30초, Task 통계 ON이다. CPU는 머신 전체 논리 CPU 대비 정상 구간 사용률이다.

| 모델 / seed | FPS | CPU | 최대 간격 |
|---|---:|---:|---:|
| radius / 42 | 14.534 | 86.65% | 150ms |
| radius / 43 | 14.295 | 85.91% | 244ms |
| partition / 42 | 17.866 | 86.70% | 204ms |
| partition / 43 | 17.238 | 82.85% | 142ms |

네 사례 모두 미갱신 Actor 0, live Task 0, 정상 종료였다. 이는 20FPS 달성이나 지연 상한 보장과 별개다.

## 2. 대기 분해

기본 비활성 진단을 추가했다. 선택된 Area에 대해 게시 직전, 큐 삽입 후, 첫 radius 시도, radius 획득 완료, update 진입 시점을 기록한다. 네 대기 구간 합이 기존 전체 Area 대기와 일치하는지도 실행 스크립트에서 검증한다.

| 구간 | 포함하는 시간 |
|---|---|
| 게시 준비 | timer callback 내 게시 준비, 게시 잠금/삽입 등 |
| 첫 시도 전 | 큐 순서, Worker 가용성, 큐 잠금, 앞선 항목의 충돌 영향 등 |
| radius 재시도 창 | 첫 획득 시도부터 성공까지; 다른 작업 실행/OS 선점도 포함 |
| batch 내부 | radius를 획득한 뒤 앞선 batch 작업 등이 끝나기를 기다리는 시간 |

순수 CAS 호출 경과도 별도로 기록하지만 CPU 실행 시간과 동일한 의미는 아니다. 첫 시도 전 대기에서 HOL 충돌과 Worker 처리량 부족의 비율까지 분리한 것은 아니다.

### 정렬 OFF, 28만 Actor 표본

각 20초, seed 42/43, 1/4096 좌표 표본이다. 초기 입장과 정상 구간 전체를 포함한 통계이며, trace OFF 성능 비교와 구분한다.

| seed | 타이머 지연 | 게시 준비 | 첫 시도 전 | 재시도 창 | batch 내부 |
|---|---:|---:|---:|---:|---:|
| 42 | 2.933ms | 0.001895ms | 42.282976ms | 0.001919ms | 0.040483ms |
| 43 | 2.931ms | 0.002162ms | 42.551305ms | 0.002252ms | 0.040438ms |

sample 수는 각각 14,491/13,194개이며, 실패 시도를 한 sample은 각각 368/335개였다. 게시 후 대기의 약 99.9%가 첫 시도 전 구간에 있었다. radius CAS 자체나 미리 획득한 batch 잠금의 보유 시간이 이 표본의 평균 대기를 지배한다고 볼 수 없다.

이동 없는 28만 Actor 대조군에서도 첫 시도 전 평균 44.873ms였다. 5천 Actor 대조군에서는 같은 구간이 0.357ms였다. 따라서 이동 인계만으로 과부하 대기를 설명할 수 없다.

초기 계측 구현은 Area별 진단 포인터를 추가했으나 OFF 대조군에도 비용 차이가 있었다. 최종 구현은 Executor의 별도 진단 map으로 옮겨 Area 객체 크기를 유지한다. map 구조는 Worker 실행 중 변경하지 않으며, 값은 큐 잠금과 Area 실행 소유권으로 보호한다. 기본 OFF에서는 진단 항목을 할당하지 않는다. 초기 계측 결과는 구간 원인 확인 자료이지 최종 구현의 성능값이 아니다.

## 3. 목적지 예약 앞당김 판단

Actor의 목표 시각을 callback 안에서 읽는 소유 스레드 전용 getter를 추가했다. 상세 추적에는 Actor deadline과 실제 Area 예약 시각을 함께 남긴다.

추적에 포착된 90ms 이상 간격 2건은 이동 0번인 Actor였으며 다음과 같았다. 각 행의 예약 차이/타이머/게시/첫 시도/재시도/batch/callback 구간 합은 Actor deadline 대비 지연과 일치한다.

| Actor | 갱신 간격 | Actor deadline 대비 지연 | Area 예약 차이 | 타이머 → 게시 | 나머지 합 |
|---|---:|---:|---:|---:|---:|
| 1586 | 90.413ms | 59.0341ms | 0ms | 58.7744ms | 0.2597ms |
| 1284 | 90.324ms | 60.1193ms | 0ms | 60.1079ms | 0.0114ms |

이 두 표본은 목적지 예약 앞당김으로 해결되지 않는다. 5분 검사의 159ms 사례를 직접 추적한 것은 아니므로 그 원인을 위 두 건과 동일하다고 단정하지 않는다. OS 대기 복귀/선점과 timer callback 처리 내부의 정확한 비율 역시 이 자료만으로 확정하지 않았다.

과부하에서는 큐 소비 전 대기가 큰 만큼, 추가 예약/깨우기를 만드는 앞당김 변경은 보류했다. 일부 이동의 예약 위상 차이가 항상 0이라는 의미는 아니며, 향후 별도 최적화 여지는 남아 있다.

## 4. 확인된 비용과 예약 묶음 개선

Actor deadline 수정 전 보관 실행 파일은 동일한 20초 대조에서 seed 42/43 각각 17.362/17.579FPS였다. deadline 수정 후 정렬 전 보관 실행 파일은 14.767/14.047FPS였다. 수정 전에는 이동 중 갱신 누락 경로가 있으므로 완전히 같은 동작의 성능 승패로 해석하면 안 된다. 그러나 새 예약 경로의 비용을 조사할 필요는 확인됐다.

기존 묶음은 같은 deadline이 연속해서 나타날 때만 합쳤다. Actor별 시각이 섞이면서 동일한 예약도 중간에 다른 시각이 끼면 별도 Task가 됐다. 새 방식은 최대 64개의 예약을 `(deadline, 원래 순서)`로 정렬한 뒤 정확히 같은 deadline만 묶는다.

- Actor/Area deadline 값은 바꾸지 않는다. 서로 다른 deadline을 같은 Task로 합치지 않는다.
- 동일 deadline의 상대 순서를 유지한다. 큐 추출의 FIFO/선두 실패 중단과 radius 획득 정책은 그대로다.
- 정렬 보조 배열은 스택에 둔다. 오브젝트 풀이나 idle Worker 관리/stealing은 추가하지 않았다.
- `AREAUPDATE_RADIUS_SORT_TIMERS=0`으로 비교용 기존 경로를 사용할 수 있다. 최종 기본값은 ON이다.

### 같은 실행 파일의 OFF/ON 비교

계측 OFF, 각 20초, 28만 Actor, seed별 실행 순서를 반대로 했다.

| seed | FPS OFF → ON | CPU OFF → ON | 생성 Task OFF → ON | 예약 건수 OFF → ON | 최대 간격 OFF → ON |
|---|---:|---:|---:|---:|---:|
| 42 | 13.432 → 16.057 | 80.65 → 87.99% | 19,188,421 → 7,521,627 | 47,950,195 → 57,595,179 | 158 → 158ms |
| 43 | 14.097 → 16.118 | 83.79 → 87.82% | 19,631,945 → 7,607,916 | 51,595,791 → 58,047,189 | 150 → 192ms |

FPS 개선은 각각 약 19.5%/14.3%였고 예약당 Task 비율은 약 0.38~0.40에서 0.13으로 감소했다. 처리량은 개선됐지만 CPU가 더 사용됐고 순간 최대 지연은 일관되게 개선되지 않았다. 정렬로 모든 지연이 해결됐다는 결론은 아니다. 각 실행의 실제 예약 건수도 달라지므로 Task 절대 개수만으로 같은 양의 일을 했다고 가정하지 않는다.

실행 간 처리량 변동이 있어 더 작은 차이의 원인이나 일반화된 성능 상승률은 확정하지 않는다.

### 최종 기본값 재검증

최종 ON 상태에서 5천 Actor의 수신자별 ID/소유권 검사를 균등/경계 각각 60초씩 다시 실행했다. FPS는 19.9983/19.9975, p99 상계는 모두 70ms, 최대 간격은 81/70ms였다. 이벤트 670,344/712,328건이 모두 적용됐고, overlap 0, 소유권 왕복 성공, live Task 0이었다. 이는 앞의 5분 검사 이후 추가된 예약 정렬의 별도 검증이며, 최종 코드로 5분 검사를 반복한 것은 아니다.

최종 별도 map 방식의 계측 ON으로 28만 Actor를 20초 실행한 결과, 유효 표본 14,816개 모두 구간 합이 전체 대기와 일치했다. 게시 준비 0.004352ms, 첫 시도 전 38.480030ms, 재시도 창 0.002254ms, batch 내부 0.040420ms였고 타이머 지연 평균은 2.719ms였다. 예약 52,335,139건을 Task 6,847,330개로 처리해 정렬 ON의 묶음 비율도 확인했다.

이 계측 ON 실행의 FPS는 14.654, CPU 85.18%, 최대 간격 161ms였다. 진단 map 조회 등 계측 비용이 포함되므로 OFF 성능 비교 값과 합산하거나 최종 운영 FPS로 사용하지 않는다. 진단은 기본 OFF다. 정렬 ON도 28만 Actor에서 20FPS 달성을 보장하지 않는다.

## 남은 범위

- 첫 실행 시도 전 대기에서 Worker의 timer/request 처리, 큐 잠금, HOL 영향의 비율은 아직 분리하지 못했다. 순수 radius CAS와 batch 보유 시간이 평균 대기의 주원인이라는 가설은 이번 표본에서 지지되지 않았다.
- 포착된 두 순간 지연은 예약 시각 차이가 아니라 timer → 게시 구간이 주원인이었다. 해당 구간 내부 OS 지연과 callback 누적 처리의 비율은 추가 실행 추적 없이는 확인 불가다.
- 28만 Actor의 처리 용량 부족은 남아 있다. 목적지 앞당김이나 더 많은 wakeup을 바로 추가할 근거로 해석하지 않는다.

## 재현 자료

- `Run-ActorDeadlineValidation.ps1`: 장시간/무결성 및 28만 Actor 검사. 현재 기본 예약 정렬 ON이며 `-SortTimers 0`으로 대조 가능하다.
- `Run-RadiusQueueProfile.ps1`: deadline 수정 전/후, 계측 OFF/ON, 이동 없음/저부하 대조군.
- `Analyze-ActorDeadlineTrace.ps1`: Actor deadline 지연과 각 구간 합 검증.
- `Run-RadiusTimerOrder.ps1`: 같은 실행 파일의 정렬 OFF/ON 비교와 ID 검사.
- 원자료: `artifacts/actor-deadline-followup/`의 `stability`, `capacity`, `queue-profile`, `timer-order`, `final`.

실게임 로직은 제공되지 않았다. 수분 단위 합성 검사이며 다시간 운영, 무누수, 무데이터레이스, 최대 지연의 실시간 보장을 증명하지 않는다.

## 빌드와 코드 검증

Release/Debug x64 솔루션 빌드, 두 구성 AreaTests, 비교 회귀 `--test`와 인계 검사, 전체 포맷 검사 및 코드 스타일 검사를 통과했다. 계측 회귀 검사에서는 첫 시도 실패 후 성공하는 공유 footprint, 시간 순서, 재게시 시 카운터 초기화와 비활성화를 확인했다. PowerShell 4개 스크립트 구문 검사와 `git diff --check`도 통과했다.

기존 프로젝트의 C++ 언어 설정을 올리지 않았고 기존 BOM/CRLF를 유지했다. Core 파일 SHA256은 기준과 동일하다. 최종 변경은 진단/재현 도구, Actor deadline 조회 getter, radius 예약 묶음 정렬에 한정된다. Actor 소유권 전환 정책과 공간 보호 모델은 이번 작업에서 추가 변경하지 않았다.
