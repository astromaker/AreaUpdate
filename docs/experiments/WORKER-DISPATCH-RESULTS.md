# 첫 실행 시도 전 대기 계측과 Worker 처리 비율 실험

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 결론

추천 순서에 따라 대기를 세분화한 후 Worker 추가 처리, 마지막으로 batch 간 예약 병합을 독립 비교했다. 두 최적화 시도 모두 본 코드에는 채택하지 않았다. 최종 변경은 기본 OFF 진단, HOL 회귀 검사, 재현 스크립트와 결과 문서다. 기존의 동일 deadline batch 내부 정렬 ON은 유지한다.

radius 잠금 범위, FIFO 선두 충돌 시 중단, batch 64, Actor 소유권, partition 공평성, ObjectUpdate 실행 정책은 변경하지 않았다. Core Worker 실험 변경은 제거했다. 오브젝트 풀과 idle Worker 관리/stealing은 추가하지 않았다.

## 조건

Release x64, Worker 8개, Task 통계 ON, signal 대기, 640×640 맵, 초당 이동 시도 8,000, 1초/1ms 분산 입장이다. 각 성능 사례는 20초씩 별도 프로세스로 순차 실행했다. seed별 OFF/ON 순서를 바꿨으며 timer trace 임계값은 20ms로 동일하게 사용했다. 부하별 실험 사이의 FPS 값을 같은 실행 파일의 A/B 결과처럼 합산하지 않는다.

## 1. 첫 시도 전 대기 세분화

새 환경 변수 `AREAUPDATE_RADIUS_QUEUE_DIAGNOSTICS=1`을 설정하면 큐 잠금 시도 실패 횟수, 방문/선두 충돌/추출 건수, 관측된 HOL 구간을 기록한다. Area 표본은 `AREAUPDATE_RADIUS_LATENCY_STRIDE=4096`으로 선택한다. 두 진단은 기본 OFF다.

관측 HOL 구간은 큐 선두의 radius 획득 실패를 처음 기록한 시점부터 해당 선두가 성공하는 시점까지다. 표본의 게시~첫 시도 구간과 겹치는 부분만 합산한다. 잠금이 중간에 이미 풀렸어도 Worker가 다시 시도하지 않은 시간이 포함된다. 따라서 순수 잠금 불가 시간이나 HOL의 인과적 기여율과 같지 않다. 보고서는 이 구간을 다른 Worker 처리 시간과 더해 인과 비율로 해석하지 않는다.

| seed | 첫 시도 전 평균 | 관측 HOL 창과 겹친 평균 | 나머지 평균 | 큐 try_lock 실패율 |
|---|---:|---:|---:|---:|
| 42 | 38.857ms | 28.326ms | 10.532ms | 11.91% |
| 43 | 39.999ms | 29.301ms | 10.698ms | 12.13% |

유효 HOL 표본은 각각 14,756/13,359개다. 실패율은 실패 시도 수 / (잠금 획득 방문 수 + 실패 시도 수)이며 시간 비율이 아니다. 첫 radius 시도 이후 획득까지의 대기와 위 선두 이전의 대기는 구분한다. 나머지 시간에서 큐 순서, mutex, Worker 가용성/선점을 다시 완전히 분리한 것은 아니다.

계측 ON FPS는 14.487/14.640, OFF는 15.403/15.598이었다. 계측 자체가 시간을 바꾸므로 ON 값을 운영 성능으로 사용하지 않는다.

### Worker 단계별 처리 시간

계측 OFF의 기존 WORKER_PHASE 기록을 합산한 값이다. 구간 경과 시간에 OS 선점 등이 포함될 수 있으므로 순수 CPU instruction 비용 비율은 아니다.

| seed | timer | request | Area/ticker |
|---|---:|---:|---:|
| 42 | 18.62% | 0.92% | 80.46% |
| 43 | 18.04% | 0.93% | 81.03% |

단순히 request 처리가 Worker를 대부분 점유한다고 볼 수 없다. timer 비용도 있지만 이미 Area 경로에 대부분의 시간이 쓰이고 있었다.

## 2. Worker 추가 처리 실험

한 번의 ticker 단계에서 250µs·최대 4 batch를 허용했다. 기존 타이머가 1ms 이내에 도래하거나 요청 대기가 256건 이상이면 추가 처리를 중단했다. 예산은 batch 사이에서 검사하므로 긴 callback을 선점하는 실시간 상한은 아니다. ObjectUpdate에는 이 옵션을 설정하지 않았다.

별도 단위 검사에서 Area 작업이 계속 있어도 요청 512개와 타이머가 완료됐고, 실행 후 설정 변경 거부 및 실제 추가 호출을 확인했다. 이 실험 전용 코드/검사는 보관 후 본 소스에서 제거했다.

| Actor / seed | FPS OFF → ON | CPU OFF → ON | 최대 간격 OFF → ON | 실제 추가 batch 호출 |
|---|---:|---:|---:|---:|
| 280,000 / 42 | 15.764 → 15.981 | 82.94 → 85.22% | 134 → 203ms | 1,084,351 |
| 280,000 / 43 | 16.310 → 16.248 | 88.18 → 87.50% | 207 → 126ms | 1,094,295 |
| 70,000 / 42 | 19.987 → 19.994 | 37.58 → 38.15% | 103 → 102ms | 510,548 |

과부하 FPS 변화는 약 +1.38%/-0.38%로 방향이 엇갈렸다. 최대 지연 역시 일관되지 않았다. 추가 경로가 실행되지 않아 효과가 없었던 경우는 아니다. 이 자료에서는 Worker 처리 비율 변경을 기본값으로 채택할 근거가 부족했다.

## 3. batch 간 동일 deadline 예약 병합

같은 Worker의 이미 등록된 Task에 정확히 같은 deadline의 Area만 최대 64개까지 추가하는 독립 실험이었다. deadline 변경이나 등록 지연 없이 Worker별 live Task 인덱스를 사용했다. 실행/취소 시 인덱스를 정리하고, 참조 상태는 공유 수명으로 유지했다. 저장소 재사용이나 Task 오브젝트 풀은 아니었다.

| Actor / seed | FPS OFF → ON | CPU OFF → ON | 생성 Task OFF → ON | 최대 간격 OFF → ON |
|---|---:|---:|---:|---:|
| 280,000 / 42 | 15.424 → 15.855 | 83.60 → 83.57% | 7,334,595 → 980,383 | 144 → 215ms |
| 280,000 / 43 | 15.985 → 16.189 | 87.73 → 85.24% | 7,491,299 → 999,930 | 132 → 142ms |
| 70,000 / 42 | 20.003 → 19.996 | 35.68 → 36.63% | 3,574,960 → 477,739 | 113 → 102ms |

예약 건수는 28만 Actor의 seed 42 OFF/ON에서 55,404,691/57,669,824건, seed 43에서 57,804,145/58,907,947건이었다. 따라서 Task 절대 개수만 같은 양의 작업으로 가정하지 않는다. 예약당 Task 비율도 약 0.13에서 0.017로 감소했다. 실제 batch 간 추가된 Area는 45,797,916/46,767,469개로 경로가 충분히 실행됐다.

Task 약 87% 감소에 비해 과부하 FPS 변화는 약 +2.79%/+1.27%였고, 이번 두 관측에서는 최대 간격이 늘었다. 7만 Actor에서도 처리량 이득은 없었다. 더 많은 반복 없이는 이 작은 차이의 유의성이나 최대 지연 변화의 인과를 확정할 수 없다. 수명 관리 복잡도에 비해 이득이 충분하지 않아 본 코드에서는 제거했다. Task 수 감소만으로 남은 처리량 병목이 해결된다고 볼 수 없다.

## 검증과 보관 자료

각 성능 실행은 미갱신 Actor 0, 종료 코드 0, live Task 0이었다. 예약 병합의 OFF/ON 각각 균등/경계 5초 ID 검사도 통과했다. 최종 코드에는 진단과 HOL 회귀 검사만 남기고 두 실험 기능은 제거했다.

- `Run-WorkerDispatch.ps1`: 현 소스의 큐/HOL 진단 OFF/ON 재현.
- `Run-WorkerService.ps1`: 보관된 Worker 실험 바이너리로만 재현. 기본 입력은 `artifacts/worker-dispatch/budget/bin/AreaUpdateExample.exe`다.
- `Run-RadiusReservationMerge.ps1`: 보관된 예약 병합 실험 바이너리로 재현. 현 소스에는 해당 옵션이 없다.
- 원자료: `artifacts/worker-dispatch/queues`, `budget`, `reservation-merge`.
- 실험 소스: `artifacts/worker-dispatch/service-source`, `reservation-source`. 실행 파일과 소스 보관본을 혼동하지 않는다.

다시 실행할 때는 기존 결과를 덮어쓰지 않도록 새 `-OutputDirectory`를 지정한다. 합성 부하의 짧은 반복이며 실게임의 성능, 무데이터레이스, 최대 응답 시간 상한을 보장하지 않는다.

## 최종 코드 검증

실험 제거 후 Release/Debug x64 솔루션 빌드, 두 구성 AreaTests와 비교 `--test`, Release 인계 회귀 검사를 통과했다. 최종 큐 진단 ON 상태의 5천 Actor 경계 배치 10초 검사도 이벤트 124,296건 전부 적용, overlap 0, 소유권 왕복 성공, live Task 0이었다.

`Format-Code.ps1 -All -Check`, `Check-CodeStyle.ps1`, 세 스크립트 구문 검사, `git diff --check`를 통과했다. Core 파일 SHA256 전체가 기존 기준과 일치하며 실험 전 Worker 소스와도 동일하다. 기존 BOM/CRLF와 C++ 언어 설정을 유지했다. 두 실험 기능의 환경 변수는 현 소스에서 지원하지 않으므로 재현에는 위에 명시한 보관 바이너리를 사용해야 한다.
