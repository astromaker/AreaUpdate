# 256슬롯 타이머 휠 1ms 비교와 지연 추적

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 변경과 조건

슬롯 수는 256개로 유지하고 SLOT_MS만 5에서 1로 변경했다.
비교 당시 설정은 1ms였다. 명목상 휠 범위는 1,280ms에서 256ms로 줄어들며
그보다 긴 예약은 overflow heap을 사용한다. 장기 예약의 성능은 이번 시험에 포함하지 않았다.

두 해상도 모두 동일한 추적 코드를 포함해 빌드했다.
Object 10,000개, 고정 50ms 주기, 추가 연산 0, 맵 121×121,
입장 기간 5,000ms·확인 간격 1ms, 이동 시도 초당 286회, seed 42다.
타이머 Worker 8개 + TaskDispatcher 8개, 논리 CPU 8개 구성이다.
Worker sleep_for(1ms), 요청·타이머 처리 예산, partition 정책은 변경하지 않았다.

## 결과

각 해상도를 30초씩 3회 실행했고 순서는 5→1, 1→5, 5→1로 교차했다.
표는 각 실행에서 계산한 지표 3개의 중앙값이지 모든 실행을 합친 분포의 분위수가 아니다.
CPU는 입장 완료 약 1초 이후 표본의 시간 가중 평균이며 전체 논리 CPU 기준이다.

| 지표 | 5ms × 256 | 1ms × 256 |
|---|---:|---:|
| 평균 Actor FPS | 20.007 | 20.009 |
| CPU | 33.65% | 34.24% |
| 타이머 지연 p50 | 8ms | 6ms |
| p95 | 18ms | 14ms |
| p99 | 22ms | 20ms |
| p99.9 | 30ms | 38ms |
| 실행별 최대 지연 | 37 / 38 / 40ms | 38 / 77 / 94ms |

일반적인 지연은 2~4ms 감소했고 FPS는 두 설정 모두 20 근처였다.
반면 큰 지연은 해결되지 않았다. 이번 표본에서는 1ms의 극단 지연이 더 컸지만,
3회 표본과 통제하지 않은 OS 부하만으로 1ms가 원인이라고 단정할 수 없다.
최초 128ms 사건 자체는 재현하지 못했으므로 그 사건의 원인을 소급 확정하지 않는다.

## 추적 방식

추적은 기본 비활성이다. 예제의 mode 다음 인수에 지연 임계값(ms)을 지정하면 활성화된다.
Worker 시작 전에 설정하고, 읽기 API는 join 이후에만 허용한다.

- 타이머별 제출·등록·만료·실행 가능 시각과 polling·선택·실행 직전 시각.
- 직전 loop의 타이머 처리, 요청 처리, Ticker, 마지막 sleep 구간.
- 현재 만료 batch의 위치·크기·앞선 callback 시간과 pending 수.
- Object의 입장 순서 ID로 타이머와 Actor를 연결한다.
- Worker마다 가장 큰 지연 32건만 보관한다. 전체 상세 기록 상한은 256건이다.
- 모든 실행된 타이머의 지연 히스토그램도 기록한다. 200ms 이상은 마지막 버킷에 합친다.

실행 중 상세 기록에는 동적 할당·파일 I/O·공유 로그 mutex가 없다.
join 이후 로그를 출력하고 측정 스크립트가 timer-traces.csv로 변환한다.
상위 지연 표본이므로 상세 로그의 단계별 건수를 전체 원인 비율로 해석하면 안 된다.
미보관 상세 기록 수는 타이머가 유실됐다는 뜻이 아니다.
추적용 Task 필드와 Actor ID가 추가됐으며 양쪽 해상도에 동일하게 적용했다.

## 포착된 77ms

1ms 두 번째 실행, Worker 2, Actor 2707:

```text
만료 시각 기준
제출             -1ms
휠 등록         +77ms
선택·실행       +77ms
```

요청 큐에서 만료 이후 대기한 시간이 77ms였고 휠 등록 후 추가 지연은 없었다.
기록된 마지막 sleep은 만료 -10ms부터 +33ms까지였다.
이미 제출된 요청이 만료를 넘겨 sleep 구간과 겹친 시간은 33ms다.
나머지 44ms를 어느 callback·잠금·OS 실행 지연이 차지했는지는 이 기록만으로 확정할 수 없다.
실행 시 Worker 요청 잔량은 873이었다.

같은 실행의 다른 57ms 사건은 휠에 미리 등록돼 있었지만 sleep 구간이 길어져
만료 이후 약 56ms 뒤 polling으로 돌아온 사례였다.
따라서 한 종류의 원인으로 모두 묶을 수 없다.

## 포착된 94ms

1ms 세 번째 실행, Worker 2, Actor 6683:

```text
제출             -47ms
휠 등록          -46ms
실행 가능·만료     0ms
직전 polling     +32ms
직전 타이머 종료 +90ms
이번 polling     +90ms
이번 선택        +91ms
실행 직전        +94ms
```

제때 등록된 타이머가 선택 polling까지 90ms 대기했고,
선택 처리 1ms와 batch 안의 앞선 처리 3ms가 더해졌다. 1ms 단위 올림 때문이 아니다.
직전 polling 당시에도 이미 기한을 넘긴 상태였으며,
직전 타이머 처리 구간의 벽시계 시간이 58ms였다.
이번 선택 batch는 처리 예산과 같은 256건이었다.
처리 예산·백로그도 확인 대상이지만 직전 batch의 개별 callback까지 모두 기록한 것은 아니다.
이 사건의 마지막 sleep은 만료 전 끝났고 현재 polling 간격에는 sleep이 없었다.

여기서 callback 구간은 실행 시간뿐 아니라 그 구간의 잠금 대기·OS에 의한 실행 중단도 포함한다.
58ms를 실제 CPU 연산 시간 또는 특정 mutex 비용이라고 단정할 수 없다.
그 내부 구분에는 OS 스케줄링 추적이나 더 세분화한 callback 계측이 필요하다.

## 추적 비용 대조

추적을 끄고 해상도별 20초를 추가 실행했다.

| 해상도 | FPS | CPU | 최대 타이머 지연 |
|---|---:|---:|---:|
| 5ms | 20.022 | 34.24% | 40ms |
| 1ms | 20.018 | 33.46% | 33ms |

각 1회이고 추적 실행과 길이도 다르므로 오버헤드의 확정 비율은 제시하지 않는다.
이 대조는 timestamp·histogram 기록을 끈 것으로, 공통으로 추가된 필드·버퍼 메모리까지 제거한 빌드는 아니다.
비활성 히스토그램 분위수는 0ms가 아니라 미측정(null)으로 저장했다.

## 검증과 자료

- 5ms/1ms 각각 Release/Debug 빌드와 AreaTests 통과.
- 해상도 경계의 조기 실행 방지, 장기 예약·대량 만료·긴 정지 후 처리 검증 유지.
- 상위 32건 보관과 최댓값 유지, 의도적인 요청 처리 지연의 추적 검증 추가.
- 타임라인 분해 합계가 실제 지연과 일치하는지 self-test 및 전체 보관 기록 검증.
- 추적 실행 6회 + 비활성 대조 2회 모두 종료 코드 0, 중복·미갱신·잔여 Task 0.
- 각 실행의 최대 지연이 임계값 이상이면 반드시 상세 기록에 보관됐는지 확인했다.
- 1ms에서 area/original/job smoke 테스트와 서식 검사 통과.

artifacts/wheel-resolution에 실행 파일·해시·환경·results.csv·각 실행의
runtime.log/samples.csv/summary.json/timer-traces.csv를 보존했다.
분석 결과는 trace-analysis.csv다. 과거 5ms 실행 파일도 유지한다.
비교 후 사용자 요청으로 현재 기본 설정은 256슬롯·5ms로 복원했다.
지연 추적 기능과 비교 자료는 유지하며 큰 지연의 별도 실행 경로는 수정하지 않았다.

```powershell
# 마지막 50은 타이머 지연 추적 임계값. 생략 또는 0은 비활성.
.\Source\x64\Release\AreaUpdateExample.exe 30 10000 286 42 5000 1 0 121 job 50
.\Measure-RuntimeCpu.ps1 -Seconds 30 -Actors 10000 -MovesPerSecond 286 -MapSide 121 -Mode job -TimerTraceThresholdMs 50 -OutputDirectory artifacts/new-timer-run
.\Analyze-TimerTraces.ps1 -RootPath artifacts/new-timer-run
```

Run-WheelResolutionComparison.ps1은 보존한 두 실행 파일로 비교한다.
Analyze-TimerTraces.ps1 -SelfTest로 분해 계산을 검증할 수 있다.
