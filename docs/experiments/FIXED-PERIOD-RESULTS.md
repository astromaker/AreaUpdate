# Object 고정 주기 예약 비교

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

이 문서는 5ms 타이머 휠에서 수행한 고정 주기 변경 실험이다.
후속 1ms 비교와 큰 지연 추적은 WHEEL-RESOLUTION-RESULTS.md에 있다.

## 변경

ObjectUpdate 런타임 예제의 예약만 바꿨다.
AreaExecuter, 예전 Area, TaskExecuter의 직렬화·round-robin 정책은 그대로다.
Worker의 sleep_for(1ms), 타이머 휠의 5ms 단위 올림과 처리 예산도 변경하지 않았다.

- 변경 전: Actor update 완료 시각 + 50ms.
- 변경 후: Actor별 입장 시 기준 시각을 저장하고, 이전 예정 시각 + 50ms.
- Worker::add_task_at으로 절대 시각을 제출한다. 기존 상대 시간 API는 그대로 유지한다.
- 다음 예정 시각이 이미 지났으면 누락 횟수를 기록하고 다음 미래 주기로 이동한다.
  지난 tick을 무제한 연속 실행하지 않는다. 실제 실행 간격이 항상 50ms가 된다는 뜻은 아니다.
- 초기 업데이트는 기존처럼 즉시 제출한다.

ObjectTickPlan.h에 계산을 분리하고 지연 17ms가 1,000회 반복돼도 기준 시각이
50ms씩 유지되는지, 경계 시각과 여러 주기 누락 처리를 검증했다.
절대 시각 예약이 예정 시각보다 먼저 실행되지 않는지도 검증했다.

## 조건

2026-10-31, Release x64, 논리 CPU 8개.
Object 10,000개, Actor당 추가 연산 0, 맵 121×121 Area, seed 42.
첫 5,000ms에 분산 입장, 확인 간격 1ms, 이동 시도 초당 286회, 실행 20초.
타이머 Worker 8개 + TaskDispatcher 8개인 기존 결합 구성이다.

변경 전 실행 파일을 보존한 뒤 before→after, after→before, before→after 순으로 실행했다.
각 버전 3회이며 독점 장비·CPU 고정·전력 상태 통제는 하지 않았다.
CPU는 입장 완료 약 1초 이후의 표본 평균, FPS는 입장 후 Actor 시간 합계 기준이다.

## 결과

| 버전 | 평균 FPS의 중앙값 | 정상 상태 CPU 중앙값 | FPS 범위 |
|---|---:|---:|---:|
| 완료 후 +50ms | 15.614 | 27.72% | 15.600~15.796 |
| 고정 주기 | 19.985 | 32.81% | 19.957~20.011 |

추가 연산과 대기 방식을 그대로 두고 평균 갱신률이 20FPS 근처로 회복됐다.
처리한 갱신 수가 늘어 CPU 사용률도 증가했다.
최초 즉시 업데이트를 포함한 유한 시간 평균이므로 수치가 20을 약간 넘을 수 있다.

## 남은 지연

| 고정 주기 실행 | FPS | 건너뛴 tick 합계 | 목표 미달 Actor | 최대 타이머 지연 | p99 갱신 간격 버킷 |
|---:|---:|---:|---:|---:|---:|
| 1 | 19.957 | 11,064 | 1,087 | 128ms | 60~69ms |
| 2 | 20.011 | 0 | 0 | 39ms | 60~69ms |
| 3 | 19.985 | 4,752 | 206 | 89ms | 60~69ms |

목표 미달 판정은 입장 시간 기준 20Hz 기대 횟수에 업데이트 1회의 여유를 둔다.
누락 tick은 모든 Actor에서 건너뛴 예정 시각 수의 합계이지 미갱신 Actor 수가 아니다.
변경 전은 고정 예정 시각 개념이 없으므로 누락 tick 값을 0으로 비교하지 않는다.

변경 전 최대 타이머 지연은 24/40/35ms였다.
변경 후 128/39/89ms로 큰 지연도 관찰됐고, 최대값이 개선됐다고 할 수 없다.
OS 부하·예약 밀도·큐 대기 등의 개별 원인은 이번 실험에서 분리하지 않았다.
변경 전 p99 버킷은 60~69/70~79/70~79ms, 변경 후는 모두 60~69ms였다.

즉 평균 20FPS 근처라는 결과가 모든 Actor의 모든 갱신을 정확히 50ms에 수행한다는 뜻은 아니다.
실제 깨우기·큐 대기 지연을 없앤 패치가 아니라, 지연이 이후 주기에 계속 누적되는 예약 방식을 고친 것이다.
70,000개 이상 인원의 고정 주기 결과는 아직 측정하지 않았다.
