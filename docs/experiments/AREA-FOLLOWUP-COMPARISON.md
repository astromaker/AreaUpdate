# Area 후속 최적화: 파티션 캐싱과 예약 묶음

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 기준과 실험 분리

1단계 카운터 실험은 `AREA-COUNTER-COMPARISON.md`에 기록했다. 이후 실험은 전부 전역 Area 카운터 OFF, Task 통계 ON을 공통 조건으로 사용했다.

- 기준: counter-off. 반복 파티션 계산과 Area별 예약 Task를 유지한 버전.
- 2단계: partition-cache. 등록 시 파티션 인덱스 계산, 같은 예약 체인에서는 재사용.
- 3단계: timer-batch. 캐싱에 더해 같은 절대 만료 시각의 연속 예약을 하나의 Task로 묶음.
- 보완 버전: timer-compact. 별도 목록 할당 없이 크기에 맞춘 고정 배열을 Task 안에 포함.

반경 2, 25개 공간 파티션, Area 실행 batch 64, adaptive 입장 1ms/10ms/max16, signal 대기, 50ms 고정 주기, Actor 소유권은 유지했다. 오브젝트 풀, idle Worker 관리, stealing을 추가하지 않았다. ObjectUpdate와 Core Worker/타이머 구현도 변경하지 않았다.

## 측정 방법

솔루션 MSBuild Release x64 실행 파일을 각각 보관했다. 실험별 seed 42는 기준→후보, seed 43은 후보→기준으로 순서를 뒤집었다. 각 실행 30초다. 측정 중 다른 빌드·테스트는 실행하지 않았다.

14만 Actor는 453×453 맵 / 초당 이동 요청 4,000, 28만 Actor는 640×640 / 8,000이다. 1,000ms 동안 1ms 간격 분산 입장, 추가 Actor 연산 0, uniform 배치다. 실제 게임 로직 성능을 뜻하지 않는다.

표의 FPS와 CPU는 조건별 2회 평균이다. CPU는 전체 논리 프로세서 대비이며 입장 완료 후 1초부터 집계한다. 정상 상태 FPS와 CPU의 집계 경계는 완전히 일치하지 않으므로 정밀한 CPU당 처리량으로 해석하지 않는다. p99 gap은 정확한 값이 아닌 히스토그램 버킷 경계다. 조건별 2회만으로 통계적 유의성을 주장하지 않는다.

원본 결과: `artifacts/area-followup-ab/cache`, `batch`, `compact`, `no-stats`. 실행 파일/PDB/해시는 같은 상위 폴더의 `bin`, `binary-hashes.csv`에 보관했다. 단계 간 실험 시점이 달라, 서로 다른 실험의 평균을 그대로 이어 붙인 단일 개선율로 해석하면 안 된다.

## 2단계: 파티션 계산 캐싱

| Actor | 기준 FPS | 캐싱 FPS | 기준 CPU | 캐싱 CPU |
|---|---:|---:|---:|---:|
| 140,000 | 19.955 | 19.994 | 48.60% | 48.27% |
| 280,000 | 14.391 | 14.742 | 70.44% | 70.14% |

28만 평균 FPS는 약 2.4% 높아졌지만 seed별 변화는 +6.1%, -1.2%로 일관되지는 않았다. 작은 평균 개선이 관측됐다는 수준의 결과다. 14만에서는 목표 FPS에 이미 도달해 차이가 작다.

Area 크기는 368→376바이트로 늘었다. 추가 저장 공간은 453×453에서 약 1.57MiB, 640×640에서 3.125MiB다. 캐싱이 무상인 최적화는 아니다.

### 수명·동시성

`request_schedule()`에서 예약 소유권을 획득한 경로만, 큐에 공개하기 전에 `m_scheduledPartition`을 설정한다. 이후 예약 체인에서는 읽기만 한다. 비활성화 후 다시 등록할 때 계산을 갱신한다. `get_partition(width)`와 공개 `get_queue_index()`는 기존 계산 의미를 유지한다.

음수 좌표 Area를 반경 1→2→0→2의 스케줄러에 재등록하는 테스트를 추가했다. 각 단계에서 초기 실행과 후속 타이머 실행이 올바른 파티션만 사용하는지 확인한다. 테스트에서 Worker 종료 후 예약 상태를 정리한 뒤 재등록한다.

## 3단계: 동일 시각 예약 묶음

`PartitionTickBatch`는 한 Area 실행 batch 안에서만 동작한다. 다음 절대 시각이 바뀌거나 64개가 차면 별도 Task로 제출하고, batch 종료 시 잔여 예약을 제출한다. 만료 시각을 반올림하거나 다른 시각으로 합치지 않는다. Area 순서도 재정렬하지 않는다.

Task는 전달받은 Area 포인터 목록을 소유하며 Actor나 Area 자체를 소유하지 않는다. Worker가 실행·취소 후 기존 방식대로 Task를 삭제한다. 영구 예약 항목이나 재활용 풀을 도입하지 않아 기존 종료 수명 규칙을 유지한다.

### 초기 vector 구현: 채택하지 않음

Task 안의 vector에 Area 목록을 복사하는 초기 구현은 별도 할당이 필요했다. 28만 Actor에서 Task 생성 수는 약 50.8% 줄었지만 평균 FPS는 14.981→14.280으로 약 4.7% 낮아졌다. CPU는 73.06→70.68%였다. Task 수 감소만으로 최적화 성공을 판단할 수 없다는 결과다. 이 구현은 실행 파일과 측정 자료만 보관하고 코드에서는 대체했다.

### 내부 배열 구현: 최종 후보

Area가 하나면 기존 단일 포인터 Task를 사용한다. 여러 개면 2/4/8/16/32/64 중 필요한 최소 용량의 배열을 Task 안에 포함한다. 별도 vector나 풀이 없으므로 예약 Task당 `new` 한 번으로 끝난다. Area 실행 batch 크기 64는 그대로다.

| Actor | 캐싱 기준 FPS | 내부 배열 FPS | 기준 CPU | 내부 배열 CPU | 기준 Task 생성 | 내부 배열 Task 생성 |
|---|---:|---:|---:|---:|---:|---:|
| 140,000 | 19.978 | 19.949 | 47.50% | 45.90% | 59,972,145 | 37,392,038 |
| 280,000 | 15.001 | 15.810 | 73.15% | 71.46% | 90,145,754 | 50,697,474 |

28만 Actor에서는 두 seed 모두 FPS가 높았으며 평균 약 5.4% 개선됐다. Task 생성 수는 14만에서 약 37.7%, 28만에서 약 43.8% 감소했다. 이 비율은 재예약 Task의 할당 감소이며 전체 프로세스 힙 할당 감소율은 아니다. 내부 배열 구현의 힙 ETL을 새로 수집하지는 않았다.

28만 p99 gap bucket은 기준 100/90ms, 후보 90/90ms였다. 14만은 기준 60/60ms, 후보 60/70ms로 한 실행에서 나빠졌다. 14만 최대 gap도 기준 최대 138ms, 후보 최대 234ms라 모든 지연 지표의 개선을 주장하지 않는다.

타이머 처리 예산의 단위는 여전히 Task이므로, 하나의 만료 Task가 최대 64개 Area를 enqueue할 수 있다는 차이가 있다. Area 실행의 파티션 입장 예산을 변경한 것은 아니다.

Task 통계가 ON이면 Task 수 감소와 함께 계측용 atomic 연산도 줄어든다. 이 영향을 분리하기 위해 통계 OFF의 캐싱 기준과 내부 배열 버전을 추가로 빌드해 28만 Actor에서 별도 비교했다.

### Task 통계 OFF 확인

| 280,000 Actor | 캐싱 기준 | 내부 배열 |
|---|---:|---:|
| 평균 정상 상태 FPS | 14.806 | 14.869 |
| 평균 정상 상태 CPU | 71.59% | 67.91% |
| seed 42 p99 gap bucket | 90ms | 110ms |
| seed 43 p99 gap bucket | 90ms | 90ms |
| 두 실행 중 최대 gap | 238ms | 308ms |

FPS 변화는 약 +0.4%로 두 번의 짧은 실행에서 의미 있는 처리량 향상을 확정하기 어렵다. CPU는 두 seed에서 각각 3.94%p, 3.42%p 낮았고 평균 3.68%p 감소했다. **계측 OFF에서 확인된 주효과는 CPU 비용 감소이지 FPS 상승이 아니다.** 지연 꼬리의 개선도 확인되지 않았다.

통계 OFF 기준 빌드는 같은 캐싱 코드에서 Area별 재예약을 유지하고, 후보는 내부 배열 묶음을 적용했다. 비교용 실행 파일은 별도 보관했다. 최종 작업 트리는 내부 배열 묶음을 유지하고 기본 Task 통계 ON으로 빌드했다. OFF 실행은 Task live 통계 자체가 없어 수명 검증 완료로 표시하지 않는다. 수명은 ON 구성 테스트에서 별도 확인했다.

## 정확성 검증

- 성능 비교 28회 모두 종료 코드 0, overlap=0, never_updated=0, pending Task=0 검증을 통과했다. 통계 ON인 24회는 Task live=0도 확인했다.
- 새 테스트는 1/2/3/4/5/8/9/16/17/32/33/64/65개 Area의 반복 예약, 세 번째 실행 후 비활성화, Task 생성·파괴 수 일치를 검사한다.
- 음수 좌표와 다른 반경으로의 재등록 테스트를 추가했다. 기존 공간 범위·공평성·타이머·종료 테스트도 실행했다.
- 최종 5,000 Actor 이동·이벤트 검증은 uniform/hotspot 각각 20초를 실행했다. 이벤트 전송·적용 수는 각각 237,960건 / 241,672건으로 일치했고, overlap=0, 소유권 등록·탈퇴 주기 통과, Task live=0이었다.
- 전체 서식 및 명명·초기화·중괄호 검사 통과. C++ CRLF와 기존 BOM은 유지했다.
- 최종 기본 설정의 Release x64 / Debug x64 솔루션 MSBuild와 두 구성의 AreaTests가 모두 통과했다.

## 최종 판단

캐싱과 내부 배열 예약 묶음을 유지했다. 초기 vector 구현은 성능 저하로 대체했다. 예약 Task 할당과 CPU 비용은 줄였지만, 28만 Actor의 목표 20 FPS는 달성하지 못했다. Area별 큐 등록과 파티션 입장 제약은 그대로이므로 이번 변경이 모든 스케줄링 병목을 해결한 것은 아니다.

파티션 캐싱은 작은 평균 개선과 저장 공간 증가가 교환 관계다. 예약 묶음은 CPU 비용 감소와 일부 실행의 지연 악화가 교환 관계다. 실제 게임 로직이 없는 합성 테스트이며, 장시간 운영·실제 게임 성능 또는 지연 무악화를 보장하는 결과는 아니다.

## 재현 예시

```powershell
.\Run-AreaStepComparison.ps1 -Baseline counter-off -Candidate partition-cache -OutputDirectory artifacts/new-cache
.\Run-AreaStepComparison.ps1 -Baseline partition-cache -Candidate timer-compact -OutputDirectory artifacts/new-compact
.\Run-AreaStepComparison.ps1 -Baseline cache-no-stats -Candidate compact-no-stats -OutputDirectory artifacts/new-no-stats -ActorCounts 280000
```

스크립트는 보관된 `artifacts/area-followup-ab/bin`의 실행 파일을 사용하고 summary의 실행 파일 해시를 확인한다. 이미 완료한 summary는 보존한다. Task 통계 OFF 빌드는 솔루션 MSBuild의 `/p:TaskStatisticsEnabled=0`을 사용했다.
