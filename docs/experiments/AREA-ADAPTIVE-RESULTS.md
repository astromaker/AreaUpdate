# 시간 제한 적응형 파티션 입장

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

이 문서는 최초 64회/25ms 설정의 기록이다. 후속 후보 16회/10ms 비교는
[후속 검증](AREA-VALIDATION-RESULTS.md)에 별도로 보존한다.

## 변경

기본 스케줄러를 적응형으로 바꿨다. 같은 실행 파일에서 fixed/adaptive를 선택할 수 있다.
Area batch 64, 파티션 공간 배치와 반경, FIFO, runner 완료 장벽은 유지한다.
Object TaskExecuter, round-robin, Actor 소유권, 오브젝트 풀/idle Worker 관리는 변경하지 않았다.

| 설정 | 기본값 |
|---|---:|
| 최초 입장 예산 | 8회 |
| 추가 승인 단위 | 8회 |
| 방문당 최대 입장 | 64회 |
| 추가 승인 시간 기준 | 1ms |
| 다른 파티션 서비스 대기 기준 | 25ms |

예산을 모두 사용했고 현재 큐에 작업이 남으면 다음 조건에서만 한 묶음 더 승인한다.
방문 경과 시간이 1ms 미만, 다른 파티션 서비스 대기가 모두 25ms 미만,
현재 승인 예산이 64회 미만이어야 한다.
추가 승인 시 Worker를 깨워 같은 파티션의 추가 batch를 병렬 실행한다.
다른 파티션으로 넘어갈 때는 모든 기존 runner가 종료돼야 한다.
스레드 수를 넘어 batch를 동시에 실행하거나 서로 다른 파티션의 동시 실행을 허용하지 않는다.

## 공평성과 시간 기준

서비스 대기는 큐가 비어 있지 않은데 batch를 꺼내지 못한 시간이다.
큐가 빈 상태에서 새 작업이 들어오면 시작하고, 작업을 꺼냈는데 큐가 남으면 그 시각으로 갱신한다.
개별 Area의 원래 enqueue 시각이나 가장 오래된 Area의 실제 대기 시간이 아니다.
Area별 실행 기회는 FIFO와 파티션 순회, 방문당 최대 64회 입장으로 보호한다.
기존의 동일한 방문당 8회 정책과는 공평성 정책이 달라졌다.

1ms/25ms는 엄밀한 완료 시한이 아니다. 기본 8회는 허용하며, 조건은 추가 승인 시 검사한다.
이미 승인된 묶음이나 실행 중인 batch는 완료해야 한다. 긴 Area::update, OS 스케줄링,
다른 파티션의 기본 batch 처리 때문에 관측 대기가 기준을 초과할 수 있다.
밀리초 clock 양자화로 추가 승인 구간의 실제 길이도 다를 수 있다.
무한히 오래 실행되는 callback이 없다는 전제 없이 시간 상한을 보장하지 않는다.

고정 모드는 이전 8회 정책을 유지하며 서비스 대기 추적도 끈다.
따라서 고정 모드의 maxPartitionServiceWaitMs는 0이 아니라 측정 불가(null)다.
갱신 간격의 max_gap_ms/p99_gap_bucket_ms는 두 방식 모두 기존대로 측정한다.
p99 gap은 10ms bucket의 하단 값이며 정밀 p99는 아니다.

## 구현과 검증

AreaSchedulingOptions로 정책을 설정하며 Worker 부착/작업 등록 전에만 변경할 수 있다.
큐의 기존 잠금 안에서 서비스 시각을 기록하고, partition 잠금 아래에서 추가 승인 여부를 결정한다.
파티션 방문 도중에는 활성 파티션을 바꾸지 않는다.
has_work와 idle_state도 현재 승인 예산을 사용하므로 추가 승인 후 잠든 Worker가 재진입할 수 있다.

고정 공평성 테스트는 fixed 모드를 명시해 8×64 제한을 계속 검증한다.
적응형 테스트는 별도로 다음을 확인한다.
- 추가 승인이 가능한 경우 16회 상한에서 1,024개 처리 후 다음 파티션 실행
- 오래 기다린 다른 파티션이 있으면 8회/512개 후 회전
- 실행 시간 기준을 넘으면 8회/512개 후 회전
- 기존 공간 안전성, 주기 예약, Actor 소유권과 Task 수명 회귀 검사

## 비교 조건

같은 Release x64 실행 파일, signal, 고정 50ms, Task 통계 ON, 상세 Area 프로파일 OFF다.
5초 분산 입장/1ms 확인, seed 42, 추가 Actor 연산 0이다.
14만/맵 453/이동 시도 4천, 28만/맵 640/이동 시도 8천을 사용한다.
20초 비교는 각 조건 fixed→adaptive→adaptive→fixed, 이후 28만을 각 60초 실행한다.
CPU는 입장 완료 후 안정 구간, 전체 Actor FPS는 입장 이후 시간 합계 기준이다.
성능 측정 중 빌드/분석을 병행하지 않는다.

```powershell
.\Run-AdaptiveComparison.ps1 -OutputDirectory artifacts/area-adaptive-repeat
# 마지막 인수로 기존 정책 선택
.\Source\x64\Release\AreaUpdateExample.exe 20 280000 8000 42 5000 1 0 640 area 0 signal 0 0 0 fixed
```

원자료와 실행 파일은 `artifacts/area-adaptive/measurements`에 보존한다.
기존 실행 파일과 AreaExecuter 소스는 `artifacts/area-adaptive/before`에 보존했다.

## 결과

20초는 각 2회 중앙값이며 p99 bucket은 실행별 범위다. bucket을 합쳐 전체 p99로 계산하지 않았다.

| Actor | 고정 FPS | 적응형 FPS | 고정 CPU | 적응형 CPU | 고정 p99 gap bucket | 적응형 p99 gap bucket |
|---:|---:|---:|---:|---:|---:|---:|
| 140,000 | 19.981 | 20.007 | 50.00% | 49.50% | 60ms | 60~70ms |
| 280,000 | 13.256 | 15.908 | 66.75% | 75.20% | 90ms | 110~120ms |

28만 20초 평균 FPS는 약 20.0% 개선됐다. 실행별 고정 FPS는 13.177/13.334,
적응형은 15.567/16.249였다. 14만은 두 방식 모두 평균 약 20 FPS다.

| 28만 60초, 각 1회 | 평균 FPS | 안정 구간 CPU | p99 gap bucket | 최대 Actor 갱신 간격 |
|---|---:|---:|---:|---:|
| 고정 | 12.809 | 68.17% | 100ms | 341ms |
| 적응형 | 17.231 | 83.49% | 110ms | 388ms |

60초 평균 FPS는 약 34.5% 개선됐다. 그러나 목표 20 FPS는 아직 미달이다.
적응형은 CPU를 더 사용하면서 처리량이 늘었지만 p99/최대 갱신 간격은 악화됐다.
모든 Actor에 동일한 갱신 주기를 제공하거나 기존보다 엄격한 시간 공평성을 보장하는 개선은 아니다.
처리량 우선의 기본 정책으로 채택하되 지연 꼬리를 우선하면 fixed 모드를 선택할 수 있다.
각 60초는 한 번씩 순차 실행했으므로 장시간/다회 무작위 실험의 결과로 일반화하지 않는다.

적응형의 최대 파티션 서비스 대기는 14만 16/19ms, 28만 20초 41/28ms, 60초 39ms였다.
개별 Area 큐 대기/Actor 갱신 간격과 다른 지표다. 25ms 기준은 추가 승인 제한이며 강제 상한이 아님을 확인했다.
60초 적응형에서 추가 승인은 319,862회, 시간 기준 거부는 245,143회,
다른 파티션 대기 기준 거부는 518회였다. 거부 수는 같은 방문의 여러 runner에서 중복될 수 있는 판단 횟수다.

## 재현과 한계

예제의 새 마지막 인수는 fixed/adaptive이며 생략 시 adaptive다.
Measure-RuntimeCpu.ps1도 같은 기본값이며 -AreaAdmissionMode fixed로 이전 정책을 선택한다.
과거 계측용 Run-AreaProfile.ps1은 재현 조건을 유지하기 위해 fixed가 기본값이다.
새 정책을 상세 계측하려면 -AreaAdmissionMode adaptive를 명시한다.
이전 고정 예산 보고서는 당시 조건의 결과로 보존하며 새 정책 결과로 재해석하지 않는다.

후속 과제는 평균 처리량 이득을 유지하면서 갱신 간격 꼬리를 줄이는 것이다.
시간/대기/입장 상한을 무조건 늘려 처리량만 높이는 방식은 권장하지 않는다.
이번 비교에는 빈번한 Actor 상호작용이나 극단적 집중 배치 부하가 없다.

## 최종 검증

Release/Debug MSBuild, AreaTests, UpdateComparison --test를 통과했다.
Release AreaTests는 병렬 장벽 테스트를 포함해 3회 반복했다.
고정 정책의 공평성 검사도 남겨두고 새 정책은 별도 guard/상한/장벽 검사로 검증했다.
상세 계측을 끈 성능 실행 10회 모두 Task 수명 검증을 통과했고 미갱신 Actor·중복 갱신·종료 코드가 0이었다.
