# 예전 Area 후속 최적화

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

이 문서는 게시 경로 개선 전 결과다. 이후 [RADIUS-PUBLICATION-RESULTS.md](RADIUS-PUBLICATION-RESULTS.md)의 묶음 게시에서 이득이 확인돼 legacy 기본값이 타이머/게시 묶음 ON으로 변경됐다. 아래 기본값 유지 판단은 당시 버전에 대한 기록이다.

## 범위

새 Area와 원본 Baseline은 변경하지 않는다. 예전 방식 최적화 경로인 legacy에만 잠금 계측, 동일 시각 예약 묶음, 추출 batch 선택 기능을 추가한다. radius 2의 대각선을 포함한 5×5 보호 범위와 큐 선두 획득 실패 시 해당 큐 중단 정책은 유지한다. Actor 소유권, 파티션 정책, 오브젝트 풀, idle Worker 관리/stealing은 변경하지 않는다.

## 계측

AREAUPDATE_RADIUS_PROFILE=64로 실행 탐색 및 알림 호출의 1/64을 시간 계측한다. 계측 OFF에서는 시간 읽기와 통계 원자 연산을 생략한다. 잠금 획득, 실패 시 rollback, 정상 해제, 획득 후 update 시작까지의 시간을 구분한다. 마지막 항목은 update 실행 시간이나 잠금 전체 보유 시간이 아니다.

알림은 전체 호출·대상·Worker::wake가 실제 대기 상태를 전환한 수를 기록한다. wake 시간은 Worker 목록 mutex 대기를 포함하며 표본 평균이다. wake 성공은 이후 작업 획득 성공을 보장하지 않는다. 실행 탐색 대비 batch 획득 비율은 별도로 기록한다.

7만/28만 진단에서 탐색 호출 중 batch를 얻은 비율은 각각 약 66.2%/76.8%였다. 표본 wake 함수 평균 시간은 약 3.71µs/2.44µs였다. 이는 동일 Worker의 wake와 다음 작업 실행을 인과적으로 연결한 측정은 아니다.

15초, Task 통계 OFF, 예약 묶음 OFF, batch 64의 진단 실행:

| Actor | 표본 획득 시도 | 표본 update | 획득 평균/시도 | rollback 총합 | 해제 평균/update | 실행 전 선점 평균/update | wake 대상 중 대기 전환 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 7만 | 256,547 | 224,556 | 230ns | 1.82ms | 98ns | 31.11µs | 1.34% |
| 28만 | 507,367 | 484,551 | 282ns | 1.51ms | 109ns | 51.74µs | 0.62% |

획득/해제의 원자 연산만이 아니라 batch 내 선점과 반복 알림도 검토할 이유가 있다. 위 표는 계측에 따른 실행 변화와 시계 비용을 포함하므로 총 병목 비중으로 환산하지 않는다. 잠금 실패가 적더라도 bitmap cache line 경합은 있을 수 있으며 이 자료만으로 하드웨어 경합 비중을 확정할 수 없다.

## 예약 묶음

Area 업데이트 결과의 예약을 현재 Worker 소유의 고정 64칸 임시 배열에 모은 뒤, 해당 실행 batch 끝에서 flush한다. 연속한 예약 중 절대 만료 시각이 같은 것만 하나의 Task로 묶는다. 다른 시각을 한 슬롯으로 강제 정렬하거나 실행 시각을 늦추지 않는다. 단일 항목은 기존 Task, 복수 항목은 2/4/8/16/32/64 용량 중 맞는 Task로 단일 할당한다. Worker가 멈춰 Task가 취소되어도 기존 Task 소멸 경로를 사용한다. 배열은 임시 예약 저장 공간이며 오브젝트 풀이 아니다.

## 실험 설정

MSBuild Release x64, Task 통계 OFF, Worker 8개, signal 대기, Actor 추가 연산 0, 1초 동안 1ms 간격 입장. 새 Area는 unlimited 파티션 입장과 고정 주기 예약을 그대로 사용한다. 14만/28만 맵은 각각 453×453/640×640이다. 변경 비교는 seed 42/43에서 실행 순서를 반전한다. 성능 비교에서는 잠금 계측을 끈다.

batch 1/4/16/64는 선점 시간 감소와 큐 잠금·알림·예약 처리량 사이의 균형을 비교한다. 공간 범위를 줄이는 실험이 아니다.

### 예약 묶음 단독 비교

각 20초, seed 42/43 평균이다. batch는 64로 고정했다.

| Actor | 개별 예약 FPS / CPU | 묶음 예약 FPS / CPU |
|---|---:|---:|
| 14만 | 19.947 / 67.95% | 19.954 / 67.53% |
| 28만 | 11.548 / 83.97% | 11.487 / 81.73% |

14만에서 Task 수는 약 28~30%, 28만에서 약 36~37% 줄었다. 처리량 증가로 단정할 차이는 아니며, 28만 seed 42 묶음 실행의 최대 갱신 간격은 388ms로 개별 예약 269ms보다 길었다. 이후 30초 최종 비교에서 편차까지 확인했다.

### batch 비교

28만 Actor, 예약 묶음 ON, 각 15초, seed 42/43 평균이다.

| batch | FPS | CPU |
|---:|---:|---:|
| 1 | 6.812 | 89.30% |
| 4 | 9.511 | 81.33% |
| 16 | 10.597 | 89.22% |
| 64 | 11.840 | 83.65% |

batch를 줄이는 변경은 채택하지 않는다. 작은 batch는 큐 추출·잠금·알림·예약 경로를 더 자주 반복한다. 선점 시간을 줄이는 것만으로 전체 처리량이 좋아지지는 않았다. 각 경로가 저하에 기여한 정확한 비중은 이 비교만으로 확인 불가다.

추가 진단으로 batch 1에서 1/64 표본 계측을 다시 켰다. 실행 전 선점 평균은 약 84ns로 낮아졌지만, 15초 동안 wake 호출은 약 3,162만 회, 대상은 약 2억 2,142만 Worker 회가 됐다. 실제 대기 전환은 약 7만 회였다. batch 64의 별도 진단에서는 wake 호출 약 649만 회였다. 두 실행의 처리량 자체가 달라 단순 배수 비교는 피해야 하지만, 작은 batch가 알림 경로를 훨씬 자주 반복한다는 점은 확인했다. 이 수치는 커널 이벤트 호출 수가 아니다. Worker::wake는 이미 실행 중인 Worker에 대해서는 atomic 검사 후 false를 반환한다.

## 실행 방법

tools/experiments/Run-RadiusFollowup.ps1의 profile, timers, batch, final, boundary 단계를 사용한다. 환경 변수 AREAUPDATE_RADIUS_BATCH는 1~64, AREAUPDATE_RADIUS_TIMER_BATCH는 0/1이며 RuntimeBackend 구성 전에만 읽는다. 통계 ON 실행을 성능 결과로 섞지 않도록 스크립트에서 거부한다. artifacts/radius-followup/profile은 이전 통계 ON 실행이 거부된 자료이며 비교에서 제외한다. 유효한 원자료는 artifacts/radius-followup-v2 아래에 있다.

boundary는 중앙 인접 2×2 Area 안에 Actor를 배치하고 이동도 이 범위로 제한한다. 네 Area의 radius footprint가 서로 겹치므로 두 모델 모두 동시 실행 제한을 받는 경우다. 이동·이벤트 probe에서도 같은 배치를 사용하되 correctness 검증과 합성 전투 부하를 구분한다. 실제 게임 로직 성능은 확인 불가다.

## 최종 교차 비교

각 30초, seed 42/43 평균이다. 기존 최적화는 이번 변경 전과 같은 개별 예약/batch 64 설정이고, 묶음 후보는 같은 실행 파일에서 예약 묶음만 켰다. Git 원본인 original과의 비교가 아니다. 원자료의 legacy-final은 최종 비교에 넣은 묶음 후보 이름이며, 채택된 기본값을 의미하지 않는다.

| Actor | 새 Area FPS / CPU | 기존 최적화 FPS / CPU | 묶음 후보 FPS / CPU |
|---|---:|---:|---:|
| 7만 | 19.989 / 24.83% | 19.987 / 38.70% | 19.991 / 38.65% |
| 14만 | 19.985 / 42.95% | 19.968 / 67.99% | 19.984 / 68.42% |
| 28만 | 19.515 / 82.12% | 12.205 / 88.93% | 12.065 / 87.26% |

28만에서 묶음 후보의 평균 FPS는 약 1.15% 낮고 CPU는 약 1.67%p 낮았다. seed 둘 모두 FPS가 조금 낮았지만 유의한 저하라고 단정할 반복 수는 아니다. 처리량 개선 역시 확인되지 않았다. 예약 Task 수는 약 34% 줄었다. peak private memory 평균은 기존 531.59MiB, 후보 527.86MiB였다. 프로세스 전체 메모리 측정이며 할당 byte 수 자체를 직접 계측한 값은 아니다.

| 28만 갱신 편차 | 새 Area | 기존 최적화 | 묶음 후보 |
|---|---:|---:|---:|
| 두 실행 중 최저 Actor FPS | 18.442 | 11.913 | 11.651 |
| 두 실행 중 최대 갱신 간격 | 205ms | 305ms | 290ms |

최대 지연의 방향은 seed/단계에 따라 달라졌다. 묶음이 tail latency를 일관되게 개선한다고 볼 수 없다. 최종 교차 비교의 미갱신 Actor는 모두 0이었다.

## 경계 밀집 비교

인접 2×2 Area 안에 7만 Actor를 두고, 이동도 이 범위에 제한했다. 각 30초, seed 42/43 평균이다.

| 모델 | FPS | CPU | 두 실행 중 최대 갱신 간격 |
|---|---:|---:|---:|
| 새 Area | 19.996 | 2.93% | 123ms |
| 예전 방식 묶음 후보 | 20.001 | 3.14% | 124ms |

두 모델 모두 약 20 FPS였다. 이 배치에서는 반경이 겹치는 네 Area가 독립적으로 병렬 실행될 수 없으므로 넓은 맵 처리량 비교와 구분한다. 예전 방식의 예약 2,400건은 Task 2,400개로 제출돼 묶음 효과도 없었다. 실행 batch 자체가 충돌 때문에 하나씩 추출되는 경우다. CPU가 낮은 이유를 이 상황에서 처리 병목이라고 해석해서는 안 된다.

계측/예약/batch/최종/경계 비교와 추가 batch 1 진단을 합쳐 통계 OFF 유효 실행은 41회다. Task 통계 ON으로 거부된 초기 자료는 포함하지 않는다.

## 채택 여부

- 기본값: 개별 타이머 예약, batch 64, 잠금 계측 OFF를 유지한다.
- 예약 묶음: Task 할당 수 감소는 확인했지만 처리량 이득이 없어 실험용 선택 옵션으로만 유지한다. AREAUPDATE_RADIUS_TIMER_BATCH=1로 켠다.
- 작은 batch: 처리량이 낮아져 기본값에 적용하지 않는다. batch 설정은 비교 재현과 검증용이다.
- 알림 정책: 비용의 추가 조사 근거는 확보했지만 lost wake 방지 조건을 임의로 제거하지 않았다. 원인별 CPU 비중까지 확정한 프로파일은 아니다.
- 결론: 이 범위에서는 새 Area가 넓은 맵의 병렬 처리에 유리하다는 비교 결과가 바뀌지 않았다. 모든 가능한 최적화의 소진이나 이론적 성능 상한을 증명한 것은 아니다.

- Release UpdateComparison --test 통과. 기존 original/object 경로의 회귀 검사도 포함한다.

- reference SHA256 목록과 대조해 새 Area 구현 및 원본 Baseline 파일이 그대로임을 확인했다.

tools/validation/Test-RadiusFollowup.ps1로 통계 ON 검증을 재현할 수 있다. artifacts/radius-followup-v2/validation에 로그, final-source에 최종 소스 복사본과 해시를 보관했다. 예약 묶음은 정확한 만료 시각과 정상 종료 경로를 검증했으며, Worker callback 예외를 복구하는 실행 모델은 추가하지 않았다.
