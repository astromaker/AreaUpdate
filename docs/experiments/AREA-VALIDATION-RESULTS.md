# Area 후속 최적화와 검증

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 범위와 순서

1. 28만 Actor에서 입장 상한/다른 파티션 대기 기준을 비교한다.
2. Worker 구간·실제 대기·입장 잠금 계측으로 대기 경로를 좁힌다.
3. 집중 입장·이동 폭주·빈번한 상호작용의 성능/결과를 검증한다.
4. 두 seed와 역순 실행으로 각 180초씩 4회 반복한다.

기본 구조, 공간 반경, batch 64, Actor 소유권, Worker 수, Object의 round-robin은 유지한다.
오브젝트 풀/idle Worker 관리/stealing은 추가하지 않는다.
측정 중 빌드나 결과 분석을 병행하지 않는다. 시스템의 다른 프로세스까지 통제한 실험은 아니다.

## 추가 기능

- 예제 마지막 인수에 slice ms, 다른 파티션 대기 ms, 입장 상한, 배치 유형을 추가했다.
- uniform/clustered/hotspot 배치를 지원한다. clustered는 중앙 5×5 Area 입장, hotspot은 중앙 한 Area다.
- 입장 완료 1초 후 누적 update 카운터를 한 번 읽고 종료 시 차이를 계산해 안정 구간 FPS를 기록한다.
  snapshot 중 동시 갱신과 종료 batch drain에 따른 오차가 있어 정밀한 deadline 준수율은 아니다.
- 기존 gap histogram은 전체 실행을 포함한다. p99 gap bucket은 10ms 하단 값이며 안정 구간만의 p99가 아니다.
- Worker phase는 타이머 추적을 켰을 때만 기록한다. OFF 성능 측정에는 추가 clock/카운터 비용을 줄였다.
- Area admission 잠금 획득 대기는 Area 프로파일을 켰을 때만 기록한다.

## 1. 설정 비교

동일 실행 파일, 추가 연산 0, 28만 Actor, 맵 640, 이동 시도 초당 8천,
5초 분산 입장/1ms 확인, signal, 고정 50ms, Task 통계 ON, 상세 계측 OFF다.
각 20초씩 2회이며 두 번째는 순서를 뒤집었다. 표의 FPS는 안정 구간 실행별 값이다.

| 설정 | 안정 FPS 1/2 | p99 gap bucket 1/2 | 최대 gap 1/2 |
|---|---:|---:|---:|
| fixed 8 | 11.529 / 12.993 | 110 / 90ms | 308 / 217ms |
| 기존 adaptive 64, 대기 25ms | 16.966 / 17.590 | 150 / 100ms | 474 / 254ms |
| adaptive 32, 대기 10ms | 15.492 / 16.086 | 130 / 120ms | 306 / 319ms |
| adaptive 16, 대기 10ms | 12.094 / 14.326 | 100 / 90ms | 256 / 230ms |

32회는 p99 개선이 두 실행 모두에서 재현되지 않았다. 16회를 보수적 후보로 선택했다.
이는 처리량을 그대로 유지하는 최적화가 아니라 긴 간격을 줄이는 방향의 정책 절충이다.
첫 비교의 표본이 적고 변동이 크므로 후속 반복 결과와 함께 판단한다.

## 2. 대기 구간의 의미

WORKER_PHASE의 timer_ns는 타이머 추출/콜백과 상세 추적 비용,
request_ns는 요청 분리/타이머 등록 등, ticker_ns는 Ticker 호출 및 그 주변 관리 비용이다.
모두 벽시계 시간이며 OS에 선점된 시간도 포함한다. CPU 샘플 프로파일이 아니다.
세 phase 합계는 같은 Worker의 busy_ns에 포함된다.

blocked_idle_ns는 wait 진입 당시 ready 작업이 있으나 runnable이 아닌 경우의 실제 대기 호출 시간이다.
구간 전체에 걸쳐 계속 같은 이유로 막혔다는 뜻은 아니다. idle_ns의 부분집합이다.
기존 blocked_return_ns와 다르게 복귀 후 타이머/요청 처리는 포함하지 않는다.
signal→대기 반환 latency에는 OS 기상 지연과 신호 병합 등이 섞인다.
admission_lock_ns는 잠금 획득 전후 clock으로 관측한 시간이며 순수 mutex 내부 비용만이 아니다.
상세 계측은 결과를 교란하므로 해당 실행의 FPS를 OFF 제품 성능으로 취급하지 않는다.

## 3. 상호작용 검증의 구분

런타임 집중 부하는 실제 예제의 AreaExecuter/타이머/Actor 입장·이동 경로다.
hotspot은 7만 Actor를 한 Area에 넣고 이동하지 않는다. clustered는 7만 Actor/이동 시도 2만,
uniform 이동 폭주는 14만 Actor/이동 시도 8만이다. 모두 20초씩 fixed/후보/Object를 비교한다.
이 예제 자체에는 damage 등 Actor 간 상호작용이 없다.

기존 UpdateComparison all 모드는 single/job/area/original의 이벤트 수와 수신 상태/체크섬을 비교한다.
기존 area 모드는 별도 tick 단위 batch 구현이므로 새 AreaExecuter 예약 정책의 검증은 아니다.

이를 보완하기 위해 area-runtime 모드를 추가했다. 실제 Core Worker와 AreaExecuter의 50ms 예약으로
고정 위치 Actor들을 갱신하고 주변 Actor에 직접 damage를 전달한다.
종료 후 각 발신 Actor의 실제 update 횟수로 수신자별 기대 damage를 재계산한다.
Actor 동시 접근 감지와 수신 상태 검증을 모두 통과해야 성공한다.
이 모드의 ticks 인수는 실행 초(최대 120)이며, tick barrier/p99_tick은 측정하지 않는다.
출력 p99_tick_ms=0은 지연 0이라는 뜻이 아니라 해당 모드에서 미계측이라는 뜻이다.
상호작용 검증과 Actor 이동 검증은 별도 시나리오이며 둘을 동시에 수행한 것은 아니다.

## 4. 반복 부하 범위

28만 Actor에서 후보/기존64회 정책을 seed 42·43으로 각 180초 실행한다.
seed 42는 후보→기존, seed 43은 기존→후보로 순서를 뒤집는다.
Task 수명·미갱신·중복 갱신을 검증하고 CPU 표본의 메모리 추이도 확인한다.
3분 반복은 수시간/수일 안정성이나 실제 게임 서버 전체 부하를 보장하지 않는다.

## 재현

```powershell
.\Run-AreaTuning.ps1 -OutputDirectory artifacts/area-validation-repeat/tuning
.\Run-AreaFollowup.ps1 -AdmissionMax 16 -AdmissionWaitMs 10 -StressSeconds 180 -OutputDirectory artifacts/area-validation-repeat/followup
```

원자료는 artifacts/area-validation/tuning 및 followup에 보존한다.

## 2단계 결과: 대기 경로

진단 실행은 28만 Actor/20초, Area 프로파일 1/64와 타이머 추적 기준 20ms를 켰다.
아래 합계는 Worker 8개의 벽시계 시간 합이다. 서로 겹치는 지표를 중복 합산하지 않는다.

| 지표 | fixed 8 | 후보 16/10ms |
|---|---:|---:|
| 타이머 구간 | 34.11초 | 38.70초 |
| 요청 처리 구간 | 3.36초 | 3.88초 |
| Ticker/주변 관리 구간 | 87.62초 | 89.81초 |
| 전체 실제 대기 호출 | 33.33초 | 26.53초 |
| 진입 시 ready이지만 차단된 실제 대기 호출 | 31.12초 | 23.18초 |
| 신호→대기 반환 평균 | 14.27µs | 15.06µs |
| 입장 잠금 획득 평균, 6~20초 | 23.19µs | 18.07µs |
| Area 큐 체류 평균, 6~20초 | 66.50ms | 54.73ms |

입장 잠금 표본은 성공/거부 시도를 모두 포함하며 각각 819,267/784,759건이다.
획득 시간 합계는 약 19.00/14.18초로 Ticker 구간에 이미 포함돼 있다.
blocked idle은 전체 idle의 부분집합이며 신호 복귀 지연도 대기 시간에 포함된다.
이들을 모두 더해 총 병목 비중으로 계산하면 안 된다.

관측상 실제 대기의 대부분이 ready 작업이 있지만 입장할 수 없는 상태에서 시작됐다.
신호 복귀의 평균 수십 µs만으로 Area의 수십 ms 큐 체류 전체를 설명할 수 없다.
입장 공유 잠금·방문 완료 장벽·대기열 처리량과 타이머 콜백 처리도 확인할 대상이다.
Ticker가 busy 시간의 큰 부분이지만 그 안에 mutex 대기와 OS 선점이 포함되므로 CPU 연산 병목이라는 뜻은 아니다.
순수 장벽/OS 스케줄링/캐시 경합의 인과 기여는 CPU/커널 프로파일 없이 확인 불가다.
진단 ON의 FPS는 fixed 10.32/후보 11.96으로 별도 조건이며 OFF 성능과 섞지 않는다.

## 3단계 결과: 집중과 이동

각 20초 실행의 안정 구간 FPS/전체 CPU다. 두 Area 정책과 Object가 같은 입력을 사용했다.

| 부하 | fixed FPS / CPU | 후보 FPS / CPU | Object FPS / CPU |
|---|---:|---:|---:|
| 한 Area, 7만 Actor, 이동 없음 | 20.01 / 2.37% | 20.07 / 2.48% | 19.66 / 88.39% |
| 중앙 집중, 7만, 이동 시도 2만/초 | 19.88 / 3.52% | 19.89 / 3.47% | 19.57 / 87.71% |
| 균일, 14만, 이동 시도 8만/초 | 19.82 / 53.59% | 19.86 / 53.91% | 17.47 / 91.95% |

중앙 집중 후보의 p99 bucket은 70ms로 fixed 60ms보다 한 칸 높았다.
모든 부하에서 꼬리가 개선된 것은 아니다. 한 Area 집중만으로 Area의 높은 CPU 사용이 필요한 것도 아니다.
이 경우는 가벼운 Actor 갱신이 목표 FPS에 도달한 조건이다.
이동 시도는 기존 예제처럼 1초마다 모아서 처리하는 burst이며 매 ms 균등 이동은 아니다.
각 조건 1회이므로 작은 차이를 확정적 우열로 보지 않는다.

## 3단계 결과: 상호작용

- 기존 비교: 2,000 Actor, 40 tick, tick당 최대 64회 상호작용, 50ms 주기,
  uniform/clustered/hotspot × seed 42/43 총 6회에서 single/job/area/original 모두 수신 상태/체크섬 일치.
- 실제 AreaExecuter: 2,000 Actor, update당 최대 64회, 10초,
  clustered/hotspot × seed 42/43 총 4회에서 수신 상태/동시 접근 검증 통과.
- 추가 실제 AreaExecuter: 5,000 Actor, update당 최대 64회, 10초,
  clustered/hotspot 각 1회에서도 통과.

| 실제 5,000 Actor | Actor 평균 FPS | 검증한 이벤트 수 | 전체 CPU 환산 | 동시 접근 위반 |
|---|---:|---:|---:|---:|
| clustered | 약 19.99 | 64,015,232 | 약 3.24% | 0 |
| hotspot | 약 19.89 | 63,680,000 | 약 5.84% | 0 |

CPU는 로그의 단일 코어 기준 값을 논리 CPU 8개로 나눈 것이다.
이 상호작용은 단순 damage 누적과 미리 만든 이웃 목록을 사용한다.
일반 게임 로직·AOI 검색·네트워크·AI 비용을 포함하지 않으며 5,000명 상용 서버 성능 보장은 아니다.
area-runtime은 컴파일된 기본 스케줄링 옵션(이번 실행 16/10ms)을 사용한다.
작은 Actor 수의 상호작용 검증만으로 모든 방문의 추가 예산 소진 상황까지 검증한 것은 아니다.
추가 승인 도중 마지막 runner를 붙잡는 병렬 장벽 회귀 검사는 별도로 유지한다.

## 4단계 결과: 3분 반복

| 정책 / seed | 안정 FPS | CPU | p99 gap bucket | 최대 Actor gap | 최대 파티션 서비스 대기 |
|---|---:|---:|---:|---:|---:|
| 후보 16/10ms / 42 | 15.209 | 74.47% | 90ms | 266ms | 39ms |
| 기존 64/25ms / 42 | 17.286 | 83.07% | 110ms | 293ms | 57ms |
| 기존 64/25ms / 43 | 17.223 | 82.86% | 110ms | 474ms | 62ms |
| 후보 16/10ms / 43 | 14.846 | 73.51% | 90ms | 361ms | 33ms |

후보 중앙값은 안정 15.027 FPS/CPU 73.99%, 기존은 17.255 FPS/82.97%다.
후보는 p99 표시 bucket을 두 seed 모두 110→90ms로 줄였지만 처리량 약 13%를 포기했다.
동일한 처리량을 유지한 개선은 아니다. 최대 gap은 환경 영향도 큰 단일 최댓값으로 별도 표기했다.
두 정책 모두 28만의 목표 20 FPS에는 미달한다. 10ms 기준도 실제 대기의 강제 상한이 아니다.
현재는 갱신 간격 우선의 보수적 기본값 16/10ms를 채택한다.
처리량 우선이면 이전 64/25ms를 명시적으로 사용할 수 있다.
과거 전체 실행 FPS와 이번 안정 구간 FPS를 직접 비교하지 않는다.

## 메모리 대조

종료 중 객체 해제 표본이 섞이지 않도록 첫 10~20초와 종료 10~20초 전 생존 구간의 평균 Private Bytes를 비교했다.

| 실행 | 첫 구간 | 마지막 생존 구간 | 증가 |
|---|---:|---:|---:|
| 후보 / 42, 180초 이동 있음 | 452.87MB | 462.29MB | 9.43MB |
| 후보 / 43, 180초 이동 있음 | 452.01MB | 463.08MB | 11.08MB |
| 기존 / 42, 180초 이동 있음 | 455.00MB | 464.54MB | 9.54MB |
| 기존 / 43, 180초 이동 있음 | 453.19MB | 465.96MB | 12.77MB |
| 후보, 90초 이동 없음 | 454.56MB | 456.70MB | 2.14MB |

모든 메인 런타임 실행에서 tasks_live/tasks_pending=0, 생성/소멸 수 일치였다.
종료 시 timer_retained_bytes=0, Actor 목록 보유 capacity는 이동 있음 약 6.41MB/없음 약 2.24MB였다.
이동 관련 목록/할당 보유와 메모리 증가의 연관이 보이지만, 90초와 180초는 같은 길이의 대조가 아니다.
Private Bytes 전체 증가 원인은 힙 프로파일 없이 확인 불가이며 장시간 plateau/누수 없음도 확정하지 않는다.
Task 누수 검증 통과만으로 모든 메모리 누수가 없다고 결론내리지 않는다.

## 최종 상태와 미확인 범위

설정 변경, 선택형 구간 계측, 집중 배치와 실제 상호작용 검증 모드를 추가했다.
Release/Debug 솔루션 빌드와 AreaTests/UpdateComparison 회귀 검사를 통과했다.
상호작용 수신 상태/체크섬과 동시 접근 검증은 별도 프로브에서도 통과했다.
추가 이동 없음 90초와 5,000 Actor 프로브는 Run-AreaFollowup.ps1 끝에 포함해 재현할 수 있다.

네 단계의 계획된 검증은 수행했지만 수시간 soak, 실제 게임 처리/네트워크,
상호작용과 Actor 이동의 동시 시나리오, 힙/커널 호출 스택 프로파일은 미확인이다.
이번 후보를 모든 지표에서 최적인 설정 또는 병목 해결 완료 상태라고 표현하지 않는다.
