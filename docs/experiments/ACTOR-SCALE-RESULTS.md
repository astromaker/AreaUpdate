# Actor 수 증가 테스트

> 보관된 실험 기록입니다. 본문의 현재·기본값은 측정 당시를 가리킵니다.
> 현행 상태는 [성능 요약](../performance.md)과 [설계 결정](../decisions.md)을 확인하세요.
> 명령어와 artifacts/ 경로는 저장소 루트를 기준으로 합니다.

## 목적과 조건

Actor 하나의 연산량을 늘리지 않고, 같은 업데이트를 수행하는 Actor 수를 늘려 규모 확장을 측정했다.
Actor당 추가 xorshift 연산은 모든 단계에서 0이다. 실제 게임 AI·전투·네트워크 비용은 포함하지 않는다.
기존 연산량 증가 실험(CAPACITY-RESULTS.md)은 합성 CPU 부하 실험으로 별도 보존한다.

- 2026-10-31, MSBuild Release x64, 논리 CPU 8개, Worker 8개, seed 42.
- 각 실행은 맵 준비 후 20초. 첫 5,000ms에 입장시키며 1ms 간격으로 확인한다.
- 맵 한 변은 ceil(320 × sqrt(Actor 수 / 70000))로 설정해 Actor/Area 밀도를 약 0.684로 유지한다.
- Area 한 칸 크기와 radius 2, 실행 색상 25개, batch 64, admission 상한 8은 유지한다.
  맵 확대는 실행 색상 수를 늘리는 것이 아니라 같은 색상에서 독립 실행할 Area 수를 늘린다.
- 이동 시도는 ceil(Actor 수 × 2000 / 70000)회/초로 Actor당 비율을 유지한다.
- 따라서 고정 맵에서 밀도만 높이는 시험이 아니라, 밀도를 유지하며 월드와 인원을 함께 늘리는 시험이다.

## 결과

CPU는 전체 논리 CPU를 합쳐 100%로 환산했다.
입장 완료 시각 이후 약 1초가 지난 250ms 표본을 시간 가중해 정상 상태 CPU를 계산했다.
FPS는 입장 후 Actor 시간 합계를 분모로 한 전체 실행 평균이므로 CPU와 측정 구간이 정확히 같지는 않다.
메모리는 프로세스 Private Bytes의 표본 최대값이며 단위는 MiB다.

| Actor | 맵 한 변(Area) | 정상 상태 CPU | 평균 Actor FPS | Private MiB |
|---:|---:|---:|---:|---:|
| 10,000 | 121 | 2.26% | 15.972 | 18.4 |
| 30,000 | 210 | 5.76% | 15.428 | 54.6 |
| 70,000 | 320 | 11.37% | 15.205 | 123.4 |
| 140,000 | 453 | 15.59% | 11.530 | 235.3 |
| 280,000 | 640 | 15.97% | 5.716 | 452.5 |
| 560,000 | 906 | 16.35% | 2.707 | 884.5 |
| 560,000 반복 | 906 | 16.34% | 2.661 | 884.8 |

전 단계에서 중복 실행·미갱신·잔여 Task는 0이다. 다만 20 FPS 목표는 전 단계에서 미달했다.
이는 기능 검증 통과와 성능 목표 달성을 구분해야 한다는 뜻이다.
단계별 1회 탐색이고 최대 인원만 1회 반복했으므로 확정적인 수용량·통계적 신뢰 구간은 제시하지 않는다.

## 실행 가능한 공간과 대기

| Actor | 종료 시 활성 Area | 색상당 최소 활성 Area | partition 제한 상태의 sleep 비율 |
|---:|---:|---:|---:|
| 10,000 | 7,263 | 265 | 40.16% |
| 30,000 | 21,801 | 844 | 52.89% |
| 70,000 | 50,720 | 1,987 | 68.93% |
| 140,000 | 101,448 | 3,944 | 95.15% |
| 280,000 | 202,763 | 8,018 | 97.29% |
| 560,000 | 405,810 | 16,034 | 98.25% |
| 560,000 반복 | 405,866 | 16,049 | 98.52% |

활성 Area는 Worker 종료 후 is_active()로 집계한 스냅샷이다.
동시에 실행 중인 Area 수나 특정 순간 큐 깊이를 뜻하지는 않는다.
sleep 비율은 전체 대기 횟수 중 blocked_samples 비율이며 시간 비율이 아니다.
이 지표의 제약과 정확한 의미는 CAPACITY-RESULTS.md에 정리했다.

14만 이후 CPU는 약 16%에서 거의 늘지 않는데 FPS는 인원 증가에 따라 크게 하락했다.
충분한 독립 Area가 존재하는 큰 맵에서도 이 현상이 나타났다.
CPU 계산 자원 부족만으로 설명하기 어렵고, 기존 partition admission·대기·재참여 경로가
우선적인 원인 분리 대상이라는 이전 관측을 Actor 수 증가 시험에서도 재확인했다.
어느 경로가 손실의 몇 %를 차지하는지는 아직 확인하지 못했다.

## 중단 조건과 메모리

100만 Actor 단계는 실행하지 않았다. 당시 보수적 예상 메모리는 약 1,836MiB,
안전 예산은 약 1,538MiB였다. 예산은 당시 가용 메모리 추정치의 70%로 잡았다.
실제 OOM이 발생한 것이 아니며, 장비의 절대 메모리 한계를 측정한 것도 아니다.
따라서 이 시험에서 CPU 포화 인원에 도달했다고 주장할 수 없다.

현재 TestObject는 Actor별 갱신 간격 히스토그램을 포함해 1,016바이트다.
이 계측 메모리를 그대로 실제 게임 오브젝트 크기로 해석하면 안 된다.

러너의 가용 메모리 계산에서 Int32 Math.Max 오버로드 선택으로 중단된 부분은
Int64로 수정하고 2GiB 초과 값으로 검증했다. 이미 완료된 결과는 보존했고,
같은 측정 도구로 100만 단계 안전 예산을 재확인한 뒤 최대 인원을 반복 실행했다.

## 구현과 재현

실행 예제에 선택 인수 mapSide를 추가했다. 기존 인수를 생략하면 기본 맵은 유지한다.
mapSide는 각 변의 Area 수이며 1~2048을 허용하고 0은 기존 기본값이다.
Actor당 연산량·맵 크기·실제 입장 완료 시각·활성 Area 분포·객체 크기를 로그에 남긴다.

```powershell
# Actor 수를 늘리되 같은 밀도·이동 비율 유지
.\Source\x64\Release\AreaUpdateExample.exe 20 140000 4000 42 5000 1 0 453
.\Measure-RuntimeCpu.ps1 -Seconds 20 -Actors 140000 -MovesPerSecond 4000 -ActorWork 0 -MapSide 453 -OutputDirectory artifacts/new-actor-scale
```

Run-ActorScale.ps1이 단계별 시험과 메모리 안전 확인을 수행한다.
기존 artifacts/actor-scale 실행 파일·결과는 덮어쓰지 않도록 보호했다.
해당 폴더에 results.csv, plan.csv, environment.json, binary.json,
각 단계 runtime.log/summary.json/samples.csv와 측정 실행 파일을 보존했다.

Release/Debug 빌드·AreaTests, 스타일 검사를 통과했다.
이번 변경은 시험 입력과 계측만 추가하며 scheduler 정책 자체는 수정하지 않았다.
