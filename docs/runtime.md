# Worker와 타이머 실행 구조

`Server/server3`의 작업 소유권, 일괄 처리 큐, 타이머 wheel 구조를 참고해 적용했습니다.
기존 Area partition 스케줄링과 Area당 하나의 실행 예약을 유지합니다.
원본 라이선스는 `ThirdParty/ServerCore.LICENSE`에 보존했습니다.

## Area 입장 예산

AreaExecuter 기본값은 무제한 입장이다. 현재 파티션의 큐가 비고 마지막 runner가 완료돼야 다음
파티션으로 전환한다. 지속 유입 시 다른 파티션의 최대 대기 시간은 보장되지 않는다.
AreaSchedulingOptions.unlimited=false로 유한 정책을 선택한다. adaptive=false이면 방문당 8회,
adaptive=true이면 방문 1ms/다른 파티션 서비스 대기 10ms 기준 안에서 8회씩 최대 16회까지 승인한다.
시간 기준은 추가 승인 판단용이며 실행 중인 batch의 강제 완료 시한은 아니다.
예제의 admissionMode 인수는 unlimited(기본), fixed, adaptive 중 하나다.
처리량은 개선됐지만 갱신 간격 꼬리는 악화될 수 있다. 수치와 공평성 의미는
[적응형 비교](experiments/AREA-ADAPTIVE-RESULTS.md)에 정리했다.
64회/25ms에서 16회/10ms로 줄인 후속 설정 비교와 검증은 [후속 검증](experiments/AREA-VALIDATION-RESULTS.md)을 참고한다.

## Worker 소유권과 깨우기

- `TaskQueue`는 여러 생산자와 하나의 소비자가 사용하는 intrusive 큐입니다.
  생산자는 작업을 등록하고, Worker는 목록을 한 번에 분리한 뒤 역순으로 정리합니다.
  루프당 최대 256개 요청을 처리하며, 생산자별 즉시 작업의 등록 순서를 유지합니다.
- 타이머 요청에는 등록 시점에 단조 시계로 계산한 절대 만료 시각을 저장합니다.
  wheel과 heap은 소유 Worker만 수정합니다. 등록 요청이 밀려도 대기시간을 새로 계산하지 않습니다.
- 새 작업, 종료 요청, Area 큐 활성화, partition 전환 시 WakeSignal로 Worker를 깨웁니다.
  대기 상태를 먼저 표시한 뒤 작업 유무를 다시 검사하므로, 검사와 대기 사이에 들어온 알림을 놓치지 않습니다.
- 깨우기 알림은 합쳐서 처리합니다. 대기 Area가 0개에서 1개가 되거나 추가 batch가 쌓일 때 알립니다.
  partition 전환 시에도 필요한 batch 수만큼만 Worker를 깨우며, 현재 호출 중인 Worker도 가용 인원에 포함합니다.
  작은 작업 하나 때문에 Worker 8개를 모두 깨우는 비용을 줄였습니다.
- 기본 signal 모드에서는 할 일이 없으면 std::condition_variable 기반 WakeSignal로 다음 타이머 만료까지 대기합니다.
  예약도 없으면 새 알림까지 기다립니다. 대기 중인 Worker만 알림을 받고 알림은 보관·병합됩니다.
  외부 Ticker는 runnable 전환 알림을 보장할 때만 supports_notifications()를 true로 재정의합니다.
  기본 false인 Ticker는 최대 1ms 제한 대기로 다시 확인하므로 기존 무알림 Ticker도 멈추지 않습니다.
  기본 m_pollingWait는 false로 signal을 사용합니다. set_polling_wait(true)를 명시하면 기존 sleep_for(1ms)를 사용합니다.
  설정은 시작 전에만 변경할 수 있습니다. 후속 Area 진단에서 poll의 복귀 지연이 확인돼 기본값을 signal로 변경했습니다.
  예제와 Measure-RuntimeCpu.ps1도 기본 signal이며, 이전 poll 실험 재현은 poll을 명시해야 합니다.
- 즉시 작업과 현재 대기 만료보다 이른 타이머 요청만 대기를 깨웁니다.
  더 늦은 타이머는 이미 정해진 기상 시점에 등록 요청을 일괄 처리합니다.
  대기 만료 시각을 먼저 공개한 뒤 대기 상태를 표시하고 큐를 다시 검사합니다.
  따라서 공개 직전 제출된 요청은 재검사에서 발견하고, 공개 이후의 이른 요청은 알림으로 발견합니다.
  이 정책에서는 미래 타이머의 등록 큐 대기 시간이 길어져도 타이머 실행 지연을 뜻하지는 않습니다.
- `stop()` 이후의 새 요청은 거부하고, 정리 단계에서 남은 작업을 취소합니다.
  이미 분리한 callback batch는 `join()` 전에 처리를 마칠 수 있습니다.
  종료 전에 수락한 요청은 큐 등록이 끝난 뒤 정리합니다.
  생산자들이 종료할 때까지 Worker 객체를 유지해야 하며, Worker는 한 번만 시작할 수 있습니다.
- `add_task()`는 요청 수락 여부와 관계없이 Task 소유권을 가져갑니다.
  같은 Task를 두 번 등록하거나 여러 Worker에 동시에 등록하면 안 됩니다.

## 타이머 동작

`WheelTimer`는 5ms 간격의 슬롯 256개로 약 1.28초 범위의 짧은 타이머를 관리합니다.
더 긴 타이머는 `PriorityTimer`의 heap으로 처리합니다.
슬롯은 Task의 연결 포인터를 사용하는 head/tail 리스트여서 슬롯별 `vector` 버퍼를 보유하지 않습니다.

슬롯 위치는 올림 계산해 요청한 만료 시각보다 일찍 실행되는 것을 방지합니다.
만료 시각이 같은 타이머의 FIFO 순서는 보장하지 않습니다.
만료 작업은 루프당 최대 256개씩 실행해 일반 요청과 partition 작업에도 처리 기회를 줍니다.

시간이 크게 경과해도 한 번에 최대 256개 슬롯만 검사합니다.
건너뛴 모든 밀리초를 반복 순회하지 않지만, 만료 작업 자체의 처리량은 작업 수에 비례합니다.
wheel과 heap은 단일 Worker 소유이므로 외부 스레드는 직접 접근하지 않고 `Worker::add_task()`를 사용해야 합니다.
5ms 슬롯 간격이 부하 상황에서 callback 지연을 최대 5ms로 보장한다는 뜻은 아닙니다.

## 고정 주기 예약

현재 Area와 Object는 Core/UpdateTickPlan.h의 고정 50ms 계산을 공유합니다.
이전 예정 시각이 1,000ms이고 완료가 1,017ms라면 다음 예약은 1,050ms이며 1,067ms가 아닙니다.
완료가 1,173ms라면 1,050/1,100/1,150ms 예약을 건너뛰고 1,200ms로 예약합니다.
지난 작업을 몰아서 실행하지 않으며 다음 예약은 계산 시점보다 미래입니다.
Area의 최초 기준은 예약 토큰을 새로 획득한 시각입니다. 비활성으로 예약이 끝난 뒤 재활성화하면 다시 잡습니다.
Area skipped tick은 Area 예약 단위이고 Object skipped tick은 Actor 예약 단위여서 합계를 직접 비교하지 않습니다.
Actor가 이동하면 Area 예약 위상과 소유권 반영 시점의 영향을 받으므로 Actor별 간격이 항상 정확히 50ms인 것은 아닙니다.
partition·반경·batch 64·공평성·Actor 소유권 정책은 바꾸지 않았습니다. original 모드는 기존 상대 예약을 유지합니다.

## 진단 정보

Worker별로 다음 누적 통계를 제공합니다.

- 즉시 실행·타이머 실행·취소 작업 수
- 남은 작업·타이머 수와 최대 요청 큐 깊이
- 최대 등록·큐 대기 지연과 타이머 실행 지연
- 실행 루프 경과시간, 유휴 대기 경과시간, 대기 횟수
- 신호 기반 대기 횟수, 알림 소비 횟수, 알림 기록부터 소비까지 평균·최대 경과시간

알림 소비 지연은 OS의 순수 깨우기 지연과 같지 않습니다. 검사와 실제 대기 사이에 보관된 알림의
대기 시간도 포함하며, Actor 실행 시작까지의 전체 지연을 측정하는 지표는 아닙니다.
기존 SLEEP 통계와 타이머 추적의 sleep 시각 필드는 호환성을 위해 이름을 유지하며,
signal 모드에서는 조건 변수 대기 구간을 뜻합니다. overshoot는 해당 대기의 목표 시각 대비 값이므로
1ms sleep 기준인 poll 모드와 총합을 직접 비교하지 않습니다.

실행·대기 경과시간은 운영체제가 측정한 CPU 사용시간과 다릅니다.
스케줄링과 잠금 대기 시간도 포함하며, 실행 중 읽은 통계는 근사 스냅샷입니다.
`AreaExecuter`는 기존 잠금 안에서 partition별로 꺼낸 Area 수도 집계합니다.

`Task`는 생성·파괴·현재 살아 있는 객체 수를 기록합니다.
모든 Worker를 `join()`한 뒤 예제는 `WORKER`, `PARTITION`, `RUNTIME` 통계를 출력합니다.
남은 작업이나 살아 있는 Task가 0이 아니면 실패로 종료합니다.

Actor 목록의 보유 capacity와 overflow heap의 동적 capacity 바이트 수도 출력합니다.
Worker 내부의 고정 wheel 저장 공간은 동적 보유 바이트에 포함하지 않습니다.
보유 capacity는 메모리 누수나 전체 프로세스 할당량과 같지 않습니다.
이 계측은 모든 할당을 추적하지 않으므로, 추가 메모리 증가는 heap 프로파일링으로 확인해야 합니다.
진단용 원자 연산 자체에도 비용이 있습니다.

## 검증

`AreaTests`에서 기존 테스트와 함께 `RuntimeTests`를 실행합니다.

- wheel·heap 경계 시각과 조기 실행 방지
- 대량 만료 처리 한도와 heap 작업이 밀릴 때 wheel의 진행 보장
- 큰 시간 경과 처리와 생산자별 FIFO
- 먼 만료 시각까지 대기 중인 Worker에 더 이른 요청을 넣었을 때 깨우기
- 종료와 등록의 경쟁, 거부된 Task 파괴, 시작하지 않은 Worker의 작업 정리
- 테스트 전용 중단 지점으로 요청 승인 직후 생산자를 멈춘 상태의 종료 처리
- 다른 partition 실행을 강제로 시도하는 동안 실행 중첩과 조기 전환 방지
- 현재 Worker의 callback이 진행 중일 때 추가 batch를 다른 Worker가 처리하는지 확인

`Source/AreaUpdate.sln`을 MSBuild의 Debug·Release x64 구성으로 빌드합니다.
기존 기준 측정 파일을 덮어쓰지 않고 측정하려면 다음 명령을 사용합니다.

```powershell
.\Run-Measurements.ps1 -StressSeconds 30 -SampleSeconds 10 -OutputDirectory artifacts/runtime-linked
```

## 변경 후 측정

최종 Release 실행 결과와 로그는 `artifacts/runtime-linked/`에 저장했습니다.
저밀도·고밀도 조건은 각각 10초씩 3회, 스트레스 조건은 30초 실행했습니다.
난수 시드 42, Worker 8개, partition 25개를 사용했고 이동 시도 설정은 이전 측정과 같습니다.
이전 결과인 `artifacts/measurements/`는 보존했습니다.

| Actor 수 | 평균 Actor FPS | CPU 사용량: 논리 CPU 하나를 100%로 계산 | 최대 private memory(MB) |
| ---: | ---: | ---: | ---: |
| 1,000 | 18.952 | 3.52% | 37.67 |
| 10,000 | 18.683 | 32.40% | 48.48 |
| 5,000: 이동 부하 스트레스 | 18.681 | 15.51% | 44.26 |

7개 실행 모두 동시 중복 업데이트, 한 번도 업데이트되지 않은 Actor, 종료 후 남은 Task가 0이었습니다.
`join()` 후 Task 생성·파괴 수가 일치했으며, 스트레스 실행에서는 2,785,137개를 생성하고 파괴했습니다.
완료된 업데이트 사이 간격의 p99는 `[50, 60)`ms 구간이었습니다.
스트레스 실행의 최대 업데이트 간격은 161ms, 최대 타이머 지연은 41ms였으므로 지연 상한 5ms를 보장하지 않습니다.

참고로 `experiments/PERFORMANCE.md`의 이전 단기 측정은 Actor 1,000개·10,000개에서 각각
평균 16.46·15.28 FPS, 논리 CPU 하나 기준 4.03%·15.65%였습니다.
업데이트 지연은 줄었지만 고밀도 조건의 CPU 사용량은 증가했습니다.
병렬 batch를 깨우는 작업과 계측에도 비용이 있습니다.
실행 시간이 다르고 외부 부하를 통제하지 않은 PC에서 비동기 이동을 처리했으므로 엄밀한 A/B 검증은 아닙니다.
5ms 단위 올림과 처리 완료 후 재예약 정책이 남아 있어 목표 20 FPS도 아직 완전히 달성하지 못했습니다.

처음 적용한 전체 Worker 깨우기는 CPU 사용량을 크게 늘려 batch 수에 맞춘 알림으로 교체했습니다.
중간 버전의 슬롯별 `vector`는 고밀도 표본에서 약 9.6MB의 타이머 capacity를 보유했습니다.
최종 intrusive 슬롯은 별도 동적 wheel 버퍼를 보유하지 않지만 고정 슬롯 저장 공간과 할당기 내부 캐시는 존재합니다.
예제의 50ms 타이머는 heap 대체 경로를 사용하지 않았습니다.
이번 단기 검증만으로 일반적인 heap 누수 부재나 밤새 실행했을 때의 안정성을 증명한 것은 아닙니다.
