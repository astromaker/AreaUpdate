# 공간 안전 범위와 실행 batch

## 현재 코드의 의미

현재 Area는 좌표 한 칸이며, `get_partition(width)`는 정규화된 나머지를 사용해 `(y % width) * width + x % width` 색상을 반환한다. 서로 떨어진 여러 Area가 같은 색상을 가지며, 한 번에 한 색상만 실행한다. 여기서 partition은 연속된 직사각형 영토를 뜻하지 않는다.

## 주변 8칸의 계산

한 Area의 업데이트가 자신과 주변 8칸을 읽거나 변경하면 영향 영역은 반경 1의 3×3이다.

```text
중심 (0,0)의 영향: x=-1..1, y=-1..1
중심 (2,0)의 영향: x= 1..3, y=-1..1 -> x=1에서 겹침
중심 (3,0)의 영향: x= 2..4, y=-1..1 -> 겹치지 않음
```

따라서 현재 색상 스케줄러의 최소 축 간격은 `2 * radius + 1`이다.

| 접근 반경 | 한 업데이트의 영향 영역 | 같은 색상 중심 간격 | 색상 수 |
|---|---|---|---|
| 1, 주변 8칸 | 3×3 | 3칸 | 9개 |
| 2 | 5×5 | 5칸 | 25개 |

이 조건은 실제 접근이 지정된 반경 안에서 끝나고, 다른 스레드가 이 규칙을 우회하지 않을 때 유효하다. 이웃 Actor의 업데이트가 다시 다른 이웃을 즉시 변경하는 연쇄 호출까지 허용하면 접근 반경을 다시 계산해야 한다. 시야가 읽기 전용이라도 다른 업데이트가 같은 데이터를 쓰면 충돌에 포함한다.

사거리가 월드 단위이면 Area 크기와 경계 위치를 고려해 실제 접근 가능한 최대 칸 수로 변환해야 한다. 현재 예제의 단위 Area와 반경 2만으로 실제 게임의 월드 단위 사거리를 확정할 수는 없다.

## 공간 묶음과 batch는 다르다

연속된 `w×h` 중심 영역 전체를 한 작업으로 처리하고 반경 r까지 접근한다면 그 작업의 전체 영향 영역은 `(w+2r)×(h+2r)`이다. 주변 8칸이면 네 방향으로 한 칸씩 덧붙이는 계산이 맞으며, 모서리도 포함한다. 다만 중심 영역만 이웃과 겹치지 않는 것으로는 충분하지 않고 확장된 영향 영역이 겹치지 않아야 한다.

현재 queue의 batch 64는 이러한 연속 공간 블록이 아니다. 이미 안전 간격을 확보한 동일 색상 Area 포인터를 최대 64개 꺼내는 실행 단위다. 이번 최적화에서는 공간 간격과 batch 64를 모두 유지했다.

## 큰 맵의 의미

맵을 키워도 색상 수 9/25는 그대로이고, 같은 색상에 속하는 공간 작업 수가 늘어난다. Active Area만 실행하므로 빈 맵 확장만으로 병렬 작업이 늘지는 않는다. 예를 들어 Actor 5,000개이면 Active Area는 최대 5,000개다. 25색상과 batch 64에서 색상당 평균 작업 수는 약 3~4개에 그칠 수 있다.

따라서 기존 조건 외에 640×640 맵에 Actor 20,000개를 분산하는 S14/S15를 추가했다. 이는 공간적 작업 수를 확보한 별도 확장성 시험이지 기존 5,000 Actor 결과와의 동일 부하 비교는 아니다.

작은 맵을 완전히 직렬화하려면 전체 월드를 하나의 작업 소유자로 실행해야 한다. 현재 코드에서 단순히 radius를 0으로 만들어 색상을 1개로 설정하면 여러 Worker가 서로 다른 Area를 동시에 실행하므로 싱글스레드가 되지 않는다.
