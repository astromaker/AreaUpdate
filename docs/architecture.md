# 구조와 안전 계약

## 모듈

Core가 Worker·Task·타이머·깨우기를 제공하며 세 실행 모델이 이를 사용한다.
AreaUpdateExample은 생성·분산 입장·이동을 포함한 비동기 런타임 예제다.
UpdateComparison은 통제된 비교와 검증용이며 예제의 타이머 실행 흐름과 동일하지 않다.
파일 구성과 빌드 관계는 [프로젝트 상세](project-structure.md)를 참고한다.

## Area 실행

Actor 등록·이동 요청 → pending 목록 → 활성 Area 예약 → 타이머 만료 → 파티션 큐
→ Worker의 batch 추출 → Area와 만기 Actor 순차 갱신 → 다음 절대 시각 예약 순서다.
비활성 Area는 예약을 이어가지 않으며 Actor 수·pending 요청·명시적 활성 상태로 다시 활성화된다.

현재 partition은 연속된 영토가 아니라 좌표 나머지로 정한 공간 색상이다.
한 색상만 활성화하고 같은 색상의 서로 떨어진 Area들을 병렬 실행한다.
반경 r의 안전 간격은 축별 `2*r+1`이며 반경 2에서는 25색상이다.
최대 64개 Area를 꺼내는 batch는 연속된 공간 블록과 다르다.

현재 기본 입장은 무제한이다. 다른 색상으로의 전환은 현재 큐와 실행 중 runner의 종료에 의존한다.
유한 입장·적응형 정책도 선택할 수 있지만 이미 실행 중인 callback을 선점하지는 않는다.

## 소유권과 상호작용

- Area의 resident Actor 목록은 해당 Area 업데이트만 수정한다. 외부 등록·탈퇴는 pending으로 전달한다.
- Actor 이동은 갱신 예정 시각을 유지한다. 원본 Area가 필요한 갱신을 처리한 뒤 목적지 소유권을 공개한다.
- Actor 포인터의 수명은 호출 측이 보장해야 한다. 탈퇴 요청만으로 즉시 파괴해도 된다는 뜻은 아니다.
- 공간 보호는 설정 반경 안의 접근에만 유효하다. 연쇄 호출·범위 밖 접근·다른 실행기의 공유 상태 변경은
  메시지 전달이나 별도 동기화가 필요하다.
- 제출한 Task의 소유권은 실행 측으로 넘어가며 거절·취소도 실행 측이 삭제한다.
  같은 인스턴스를 여러 큐에 동시에 넣으면 안 된다.

## 나머지 실행 모델

최적화된 예전 Area는 미리 구성한 공간 footprint의 bit mask를 획득하고 업데이트한다.
큐 선두가 공간 잠금을 얻지 못하면 뒤를 건너뛰지 않는 공평성 정책을 유지한다.
ObjectUpdate는 Actor별 실행기를 직렬화하고 Dispatcher에 round-robin으로 재전달한다.
이 정책은 유휴 Worker 목록이나 stealing을 사용하지 않는다.

## 확장 시 재검증

현재 Actor 갱신 정책은 50ms 고정 주기이며 지난 tick을 건너뛴다. 서로 다른 주기나 시간 보정이
필요한 로직에는 별도 정책이 필요하다. Worker 자체는 임의 절대 만료 시각을 지원한다.
한 Area의 긴 callback은 같은 Area의 Actor와 파티션 전환을 지연시킬 수 있다.
또한 AreaManager는 전체 격자를 생성하므로 희소·스트리밍 월드는 저장소 설계를 별도로 검토해야 한다.

[공간 계산](spatial-scheduling.md)과 [Worker 상세](runtime.md)에 추가 계약을 기록했다.
